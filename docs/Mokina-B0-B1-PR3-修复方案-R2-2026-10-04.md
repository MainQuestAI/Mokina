## 2. F1 发送闭环（P1-1、P1-2）

### F1.1 「待确认」的显式出口：重新发送 / 放弃这条

行为规格（替换现有“只有核对”状态）：

```text
unknown + 有完整快照
  ├─〔重新发送〕（显式点击，唯一允许的同 ID 重发路径）
  │   → 先只读核对（复用 queryRunAccepted，10s 超时）
  │       ├─ 查到受理 → 走现有恢复（清记录、按快照 user/assistant id 重挂原 run），不发 POST
  │       └─ 查不到 → 用原 clientRequestId + 快照全文走现有发送管线
  │             ├─ 202 reused（含 accepted）→ 现有 onRunCreateAccepted 清记录
  │             ├─ 409 / 其他 definitive 4xx → markSendRequestDraft（现有分类）→ 出现〔恢复未发送草稿〕，正文取快照全文
  │             └─ 又丢响应 → 保持 unknown，界面不变（不自动重发、不换 ID）
  └─〔放弃这条〕→ 显式清除本地记录并解除重试拦截；文案提示“服务端可能已经受理，放弃只解除本机待确认”

unknown + 无快照（旧预览记录）→ 只给〔放弃这条〕
draft + 有快照 → 保留〔恢复未发送草稿〕，并补〔放弃这条〕
requiresContextReselection 的记录 → 不给〔重新发送〕（快照里没有插件/临时附件语义，静默重发会丢上下文），
  只给“恢复草稿（需重选上下文）”+〔放弃这条〕
```

实现落点：

1. `send-request-state.ts`：`savePendingSendRequest` 增加 `allowExisting`（同 ID 重写为 `status:'pending'`、`phase:'prepared'`、刷新 `createdAt`、重新登记 owner）。否则 `:76` 的重复判断会把“重发”直接判成保存失败。可选实现为独立 `resaveSendRequestRecord`，但语义必须是“重写同一请求身份”，不是无痕换 ID。重写路径**不计入容量判断**：它不新增记录，且若按 F1.2 只数 pending，也要把自身排除——否则 8 条在途时重发会被自己要修的容量闸挡住，死路换了个位置复发。
2. `ProjectView.tsx`：`pendingSendNotice`（`:13774-13790`）对 unknown 增加两个动作；新增 `resendPendingSendRecord(record)` 调用现有 `handleSend`，`meta.clientRequestId = record.clientRequestId`，并带上 `snapshot.userMessageId/assistantMessageId`（`ProjectChatSendMeta` 已有这两个可选字段，`:461-464`；现有恢复映射按 `clientRequestId` 回接消息，`:8485-8495`）。快照 → 发送参数的字段映射（prompt / attachments / commentAttachments / quotes / skillIds / context）复用现有 `sendRecoveryRequest` 恢复链路（ChatPane `:2745-2760`）的那套映射，不另造一份。新增一次性放行标记（如 `meta.explicitResendOf` 或 ref 白名单），让 `:8534`、`:11228`、`:11256` 三处守卫只对该次显式重发放行；普通重试与换模型继续被拦。「查到受理 → 恢复」分支必须与挂载 effect 的对账循环（`:8476-8499`）共用同一段恢复代码（提取共享函数），不复制第二份。
3. 〔放弃这条〕复用 `clearSendRequestRecord`（`:136,153` 已同时清 owner），按钮出现后由 `SEND_REQUESTS_CHANGED` 驱动重渲染；清除后普通重试恢复可用（会换新 ID——文案必须写明）。放弃只清本地记录与提示条；聊天里的消息和失败气泡按现行「失败历史保留」语义不动（与 P3-2 的浏览器实测一起观察是否需要补充清理，本轮不扩）。
4. i18n 新增 4 键（建议名）：`mokina.pendingSend.resend`、`mokina.pendingSend.discard`、`mokina.pendingSend.discardNotice`、`mokina.pendingSend.notRecoverable`；Dict + 19 locale + `i18n:check`。

先落的红测：

- `apps/web/tests/runtime/send-request-state.test.ts`：同 ID 重写不增加条数且回到 prepared/pending；`allowExisting` 缺省仍拒绝重复。
- 新文件 `apps/web/tests/components/ProjectView.pending-send-exit.test.tsx`（沿用 `ProjectView.retry-gating.test.tsx` 的 mock 宿主与 fetch 桩）：
  1. 待确认 + GET 空 → 点〔重新发送〕发出一次 POST，且请求体 `clientRequestId` 等于原 ID、prompt 为快照全文；
  2. 待确认 + 服务端已受理 → 重发得到 202 reused，断言 run 数仍为 1、消息回到原 assistant id；
  3. 待确认 + 重发 409 → 记录转 draft，〔恢复未发送草稿〕可把 >120 字正文完整放回输入框；
  4. 点〔放弃这条〕→ 记录清除，普通重试不再被拦（`retryPending` 正常出现）。

验收（对审查 F1 第 1、2 条）：浏览器故障注入沿用第一轮做法（真实 daemon、截留 POST 响应、GET 空 → 显式重发 → 递送原 POST），证据给 JSON + 截图，断言只有一个 run、原 run 身份被复用。另补一个「原 run 已终态」用例：服务端早已受理并跑完，显式重发收到 202 reused 后不得起第二个 run，会话按既有 reattach/刷新路径恢复。

### F1.2 8 条上限改为只统计 in-flight

- `savePendingSendRequest`：容量判断改为 `records.filter(r => r.status === 'pending').length >= MAX_RECORDS`；unknown/draft 不占额（它们不再阻断新发送）。
- 不淘汰任何旧记录（保持第一轮 I9/I11 的“拒绝而不挤掉未确认请求”）；unknown/draft 的清理交给〔放弃这条〕。
- 无界增长防护：新增每 scope 总记录软上限（建议 24，含 unknown/draft）。到软上限时**不阻断发送**，按 F1.3 的 `skipped` 处理（不保存新快照 + 提示不可自动恢复）。这条只用于兜住 localStorage 配额，不改变任何已存记录。
- in-flight 真到 8 条时（同一会话 8 个并发在途，现实中不可达）同样按 `skipped` 放行发送，不再出现“消息发不出去”。

红测：预置 8 条 unknown 后第 9 条 `savePendingSendRequest` 返回 saved；预置 8 条 pending 时返回 skipped（而不是 failed）；软上限外仍可发送。

### F1.3 大小上限不再拒发（只降级恢复能力）

- `savePendingSendRequest` 返回三态结果（建议 `'saved' | 'skipped' | 'failed'`）：
  - `saved`：现有行为。
  - `skipped`：正文 >64Ki、extras 被 sanitize 截断（>20 批注 / >50 附件 / >20 引用 / 未知 workspaceItems）、extras 序列化 >64Ki、或命中软上限 —— 不保存快照，但**照常发送**。
  - `failed`：仅 `localStorage.setItem` 抛异常（配额满/隐私模式）。保持现有“撤回乐观消息、还草稿、报 `saveFailed`”，这是 Spec §10「pending 写入失败不发送」的唯一保留分支。
- `ProjectView.tsx:9131-9156`：`skipped` 时不撤回、不报错，改为非阻塞提示 `mokina.pendingSend.notRecoverable`（“这条不会保存可恢复快照，刷新后无法自动恢复”）。
- 关键坑：`:8705-8718` 的 `onBeforeRunCreate` 依赖 `markSendRequestDispatched` 成功，`skipped` 时无记录会返回 false 导致发送中止。用 per-send 标记（如 `mokinaReceiptSkippedRef`）让该分支只拦截 `failed`。
- 三态改造的波及面：`persistPendingSendRequest` 包装与 `:9143`、`:9147`、`:8725`（`if (!mokinaSendRecord) return`）等布尔判空处同步改；`markSendRequest*` / `clearSendRequestRecord` 对不存在的记录是 no-op（`:109-127`、`:136-141`），`skipped` 分支不会误写存储。
- 行为对齐原生：无快照的失败只表现为普通失败气泡 + 重试（换新 ID），与原生 OpenDesign 一致；不新增自动重发。

红测：100Ki 正文、25 条批注、60 个附件、>64Ki extras 四种输入都完成 POST（fetch 收到 202）且只出现“不可自动恢复”提示，不出现 `saveFailed`；`setItem` 抛异常时仍不 POST。
