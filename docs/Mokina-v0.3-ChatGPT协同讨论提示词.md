# Mokina v0.3：ChatGPT 协同讨论提示词

日期：2026-09-14

用途：在 ChatGPT 的 Mokina 项目中，独立讨论开源产品复用与营销工作台设计。以下按顺序使用；首轮先建立判断，不一次性发送所有追问。不要求 ChatGPT 迎合 Codex，也不把模型回复当成用户批准。

## 使用方法

首轮发送“提示词一”，同时附上本文件，或将“背景与证据包”一起粘贴。首轮回答后，仅在需要继续讨论时选择提示词二或三。提示词四用于收敛已经讨论过的意见，不应提前生成实施批准。

## 提示词一：独立判断复用方向

```text
请作为 Mokina 项目的产品与技术讨论伙伴，独立评审下面的“背景与证据包”。这次只讨论产品设计与开源复用，不写代码、不生成新原型，也不要直接给出庞大的开发计划。

核心问题：面向营销专业人士，我们应该学习、调整、复用 OpenDesign 和 AionUi 的哪些现成能力？哪些业务要求确实需要补齐？不要为了独特性重造工作台，也不要因为功能看起来齐全就直接认定某个仓库适合作为底座。

请先用你自己的判断回答，再对照 Codex 的当前假设；欢迎反对“优先验证 OpenDesign”。明确区分用户已确定的要求、已核对的资料/源码事实、你的推导和仍需实测的假设。你没有被授予本地仓库或文件系统访问；如能读取公开来源，请给出实际读取的链接，不能访问则如实说明。

请回答：
1. 首版优先服务哪类营销人员、哪几项高频工作？先给合理建议，不把细分用户尚未明确当成停止讨论的理由。
2. 按“原样保留、调整后复用、检查缺口后补齐、暂不引入”列一个具体清单。每项解释用户会怎么操作、复用哪层能力，以及最关键的未知项。
3. 画一个简短文字工作区示意：日常打开看到什么；讨论、读成果、改段落、改排期、查看来源时怎样变化。不为每个状态另建页面，不增加强制审批。
4. 比较三条路线：直接 Fork 一个主底座、先以插件/扩展适配、只借鉴交互并抽取模块。给出当前推荐和能推翻推荐的条件，别把验证顺序说成已完成选型。
5. 设计一个最小但能区分路线的实际验证。说明输入、操作、预期结果、失败意味着什么。避免先大改底座后才测试，也不要求先跑完所有竞品。
6. 指出 Codex 当前判断中最值得质疑的三点，以及哪些 v0.3 既有要求可能应当简化而不是照搬。

中文回答，约 1800—2500 字。结论先行，最多两个表格。不要评估人力投入，不给虚假的性能/工期分数。不以“设计师 vs 营销人”的标签替代具体工作差异。最多提出三个真正影响下一步的待决策问题。
```

## 背景与证据包

### A. 产品与当前决策

Mokina 是营销专业人士使用的通用 Agent 工作台。要支持从目标与资料出发，持续讨论、按需计划、制作成果、局部修订、查看版本并选择部分成果继续工作。当前重点是明确开源复用方向及下一版交互，不是在本轮直接实施。

早期 0.2.x 是沿用美的/Lilith V6.2 外壳的 HTML 原型。用户现在明确要 Mokina 自身的 UI，旧版保留为行为案例和合成资料来源，不再要求保留其视觉外壳。v0.3 设计规范和设计包已有草案，但不应把草案每一条都当成不可修改的产品真理。

### B. 用户明确要求

- 面向 Marketing 专业人士，优先让实际工作可用，再迭代。
- 不排斥产品形态相似，接受学习、调整现有功能，乃至直接修改 OpenDesign、AionUi 的开源代码。
- 目的在于降低试错成本；关键是想清楚学什么、参考什么、复用什么，而不是强调差异性。
- 本轮竞品研究以开源项目及开源部分为主，纯商业产品暂不关注。
- 后续设计资产改用 OpenDesign MCP 管理，新建设计项目。使用 OpenDesign 作为设计工具，与选择其代码为产品底座，是两个不同决定。
- 当前尚未决定 Fork 哪个仓库，也没有批准把两套会话/运行/存储系统合并。

### C. 既有工作要求与讨论案例

核心要求：目标可以直接进入工作；项目可空；产品型号等信息不自动触发上市流程。解释不新增成果版本，保存计划不执行，查看版本不自动采用。已有成果应能查到当时依据。允许简单直接编辑，不把所有工作变成审批流程。

主线验证建议：两份合成访谈 → 讨论用户流失原因 → 制作备忘录 → 只修改第二个方向 → 原稿可查 → 选择该方向另开工作，形成两版邮件草稿。

社媒检验：五条文字内容与排期是可编辑的结构化成果；只缩短第三条正文，其余正文和日期、渠道等字段不变，指定版本可导出。

分析检验：真实解析 CSV，明确前后期，展示口径、分组及局限；选择结论再继续内容工作。现有合成样例的总体互动率是 5.25% → 3.875%，实用内容为 6% → 6.5%，产品介绍为 3% → 3%，实用内容曝光占比为 75% → 25%。这些是案例预期值，不是已提供 CSV 的独立验算证据，也不是因果证明。

讨论时可质疑交互复杂度，但不能用假成功、引用漂移或静默覆盖旧稿来简化产品。

### E. Codex 当前假设，可被反驳

1. 优先验证 OpenDesign 作为主底座，因为成果制作、编辑、版本、导出及品牌规则较接近当前方向；AionUi 做同一工作对照。不声称已证明维护成本或发布速度。
2. 先保留现成工作台，重点调整营销入口、业务成果编辑器、资料/来源选择及固定版本接续；不先设计全套全新 UI。
3. 一次只选一个主会话、运行和存储底座，不先合并两套系统。
4. 在隔离的上游副本验证最小营销适配，再决定完整 Fork、扩展适配或抽取模块；是否已有足够扩展点尚未检查。
5. 旧 Mokina HTML 作为行为案例和数据参考。业务语义尽量保留，但不因旧模型存在就增加一个与新底座竞争的工作生命周期。

## 提示词二：只追问最关键的分歧

```text
请继续讨论上轮最影响路线选择的分歧，不再重复整体分析。

分歧是：[填写一个具体分歧]
你的建议是：[准确复述对方观点]
Codex 的不同判断是：[填写理由与现有证据，不编造实测]

请给出：双方各自依赖的假设；一个营销人员的具体操作例子；什么观察结果会支持或推翻各自判断；能最小化改动的验证方法。若你认为两者可以兼容，请给出具体边界，而不是折中口号。不要把你的建议写成用户已经同意的决定。
```

## 提示词三：检查是不是过度设计

```text
请站在每天实际做营销工作的人的角度，审查我们刚讨论的方案。
用“读访谈并形成备忘录”“缩短社媒第三条”“从数据结论继续写邮件”三个例子逐步走一遍。

每一步说明用户看见什么、点击/输入什么、系统保存什么。指出哪些操作能复用上游原状，哪些只需改文案或配置，哪些必须有新业务逻辑。
尤其检查：是否强迫先建项目/品牌；是否为了可追溯堆出审批；简单修改是否被候选与采用拖慢；是否把所有成果做成只能预览的 HTML；是否用换壳掩盖真实状态缺失。
最后删去三项不值得首版加入的复杂度，并说明删掉以后哪些用户行为依然必须可靠。不要自动删减已明确需要的资料真实读取、原稿保存和引用一致性。
```

## 提示词四：收敛为下一步验证单

```text
请根据本次已完成的讨论收敛，不引入新的平台愿景。

输出五部分：
1. 用户已确定的要求；
2. 两方暂时一致但仍待验证的建议；
3. 仍存在的分歧；
4. 下一步最多五项验证，每项含目的、输入、操作、成功/失败信号及对选型的影响；
5. 真正需要用户决定的问题，最多三个。

不要把“建议先验证 OpenDesign”写成“已经采用 OpenDesign”，不要把两方一致当成用户批准，不把文档/源码证据升级为运行或视觉验收。给一个你当前倾向的路线，并明确何种结果会让你改选。
```
