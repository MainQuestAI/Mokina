# Mokina v0.3：专业营销体系与分发增长补充调研

日期：2026-09-14。性质：研究与方向建议，不是实施批准或产品验收。

更正：用户所述是伊美尔客户，不是 Email 渠道；由该误读推导的邮件优先及质量样板优先建议已撤回。当前先讨论营销场景的统一抽象与 Mokina 产品形态。文中邮件 Skill 的客观研究保留，不代表用户场景优先级。

配套文件：[Marketing 能力包与开源 Skill 候选清单](Mokina-v0.3-Marketing能力包与开源Skill候选清单.md)。已有底座研究：[OpenDesign 专题与复用建议](Mokina-v0.3-OpenDesign专题与复用建议.md)。

整合更新：结合网页版《讨论产品复用方向》完整回复和用户最新意见，后续讨论以[产品方向收敛与专业质量体系](Mokina-v0.3-产品方向收敛与专业质量体系.md)为结论入口。本文件保留为调研底稿；其中候选、优先级和下一步均不是已批准开发范围。

## 1. 本轮重新确定的问题

用户补充：在多个客户项目中，包括伊美尔客户，已经验证相关需求；部分客户可能愿意承担接近或超过百万元人民币的定制开发成本。本轮接受这些项目经验作为需求依据，不再安排额外访谈，不将“再验证需求”作为推进前置条件。这是用户提供的业务背景，不等同于本轮审计过的合同、回款或公开市场收入。

本轮研究三个问题：

1. 能否像 Open Design 一样，把专业规范、方法、成果形态和精修机制做成产品的默认能力，提高首稿一次可用率与整体交付质量？
2. 哪些开源营销 Skill 可以直接成为候选，哪些需要结合中文营销、品牌策略和既有项目经验改写？
3. 专业能力资产能否同时成为流量入口，把已经存在的项目需求扩展到更多同类客户？

修正上一轮的重心：不能只用“通用 Agent 已经很强”推导专业产品没有价值；专业知识是否被可靠调用、是否落实到完整成果、是否能持续精修，是独立的产品价值。市场关注点从需求是否存在，转向专业能力如何产品化、如何让目标客户发现和使用。

## 2. 核心结论

建议将 Mokina 理解为“专业营销工作系统”，而不只是“营销版聊天工具”：

> 可复用的营销规范与方法 + 客户事实与品牌背景 + 可编辑的成果工作面 + 专业检查与精修 + 可接入已有 Agent 的运行能力。

Open Design 值得优先作为业务架构和技术底座候选。学习重点不只是界面，也包括把专业内容放在可维护、可选择、可组合的资源包中，再由工作台承接运行和成果。是否直接 Fork、抽取模块或做插件，仍需实际运行与适配检查，本轮不更改选型状态。

本轮补上一个重要竞争与分发案例：Corey Haines 的开源 Marketing Skills 与 Magister 营销 Agent。它呈现出“公开方法库—开发者生态—商业工作产品”的连接方式。这个案例说明专业 Skill 既可成为产品内容，也可成为发现入口；没有公开转化数据，不能推断其商业成功程度。[S8][S11]

## 3. Open Design：用户提到的两块能力，源码支持到哪里

### 3.1 预制的不只是 Token，而是多层专业资源

本轮核验官方源为 `nexu-io/open-design`，固定提交为 `39d9eb593ba41037d1900e73f0e62489ef8ac5c1`。GitHub 完整文件树返回 `truncated: false`。按下列路径统计：

| 对象 | 固定文件树计数 | 正确理解 |
|---|---:|---|
| `design-systems/*/DESIGN.md` | 152 | 设计体系规范文件，不是 152 个 Token |
| `design-templates/**/SKILL.md` | 114 | 该目录中的模板定义文件，不代表全产品模板总数 |
| `skills/**/SKILL.md` | 163 | 该目录中的技能文件，包含嵌套资源；不等于 UI 可选技能数 |

官网插件目录另列 152 个 Systems、292 个 Templates、23 个 Skills。两者是目录、派生条目和分类口径，不应相加或互相当作错误，更不能把数量当质量验收。[S1][S2]

抽查 `design-systems/agentic/manifest.json`，一个包声明了 `DESIGN.md`、CSS Token、JSON Token、Tailwind、组件示例、使用说明、预览和来源文件。`DESIGN.md` 包含配色、字体、间距、布局、组件、交互、语气与反例等九类说明。它不是“让模型自己猜风格”，而是提供了可复用起点。[S3]

但有规范并不等于每次生成都会遵守，更不等于客户接受了成果。本轮没有运行它的生成效果测试。

### 3.2 从资源存在到实际生效，中间有运行组织层

源码中的 Skill 注册表读取本地资源，支持用户资源优先于内置同名资源，也保留旧 ID 别名。策略包加载器只读取清单声明的资源，记录包哈希与内容摘要，加载时核对绑定身份，避免旧包标识搭配已变化正文。[S4]

这对 Mokina 的意义是：

- 方法可以随着专业经验更新，而不必每次改工作台代码。
- 客户可以有自己的品牌规则与方法扩展，不覆盖通用默认包。
- 一次工作必须记录实际采用的方法版本、品牌规则和资料，才能解释结果与复现修订。
- 不应默认把整个技能库塞给模型；按任务选择主方法和必要检查即可。[S13]

### 3.3 编辑、版本与精修应分开理解

Open Design 有文件工作区、手动编辑、版本查看等实现；前一份专题已经逐项记录。本轮另核查 `patch-edit`：其实现约束计划步骤可修改的文件，处理局部 diff，并写入步骤记录。这是“受控精修”的可参考机制，不代表已支持营销条目级语义。[S5]

一个重要更正：固定提交里的 `apps/daemon/src/critique/rollout.ts:104–107` 设置 `CRITIQUE_THEATER_RETIRED = true`，使旧评审剧场总开关返回关闭。文件开头仍保留旧阶段说明，因此不能只看到组件和注释就认定评分面板当前启用。[S6]

与此同时，`critique-theater/SKILL.md` 仍描述五维质量检查，要求修复具体问题、停止无收益迭代，并用普通语言交付；它明确反对虚构评委、评分剧本和协议文本。[S7]

所以可迁移的实践是：**专业质量检查、局部修正、变化可审阅、原稿可保留**。不必复刻旧“评委打分”界面，也不能将模型自评分当作用户认可。

## 4. 营销领域如何对应这套体系

这里不建议把所有理论都叫“Marketing Token”。有些是稳定约束，有些是判断方法，有些是成果结构，职责不同。

| Open Design 层次 | Mokina 对应层次 | 示例 | 主要改善什么 |
|---|---|---|---|
| Token / DESIGN.md | 品牌与表达规范包 | 品牌称谓、语气、术语、可用承诺、禁用表达、视觉引用 | 品牌一致性、低级错误 |
| Design System / 使用指南 | 营销背景与决策依据 | 目标受众、竞争替代、差异价值、已确认方向、证据 | 内容相关性与策略一致性 |
| Skill | 专业方法包 | 市场研究、定位、Message House、文案、Email、Slogan | 首稿的专业判断与结构 |
| Template / Components | 成果蓝本与编辑器 | 策略备忘录、邮件序列、信息主张表、内容日历 | 完整交付而非零散回复 |
| Critique / Refine | 专业质检与精修 | 证据核对、表达检查、跨稿一致性、局部改写 | 成果整体质量与修订可靠性 |
| Runtime / Workspace | 运行与工作管理 | 当前资料、计划、取消、版本、导出、选择性复用 | 可操作、可恢复、可接续 |

### 4.1 规范包：把“专业默认值”与“客户事实”分开

可预制的是行业/场景的工作方法、常用成果结构、评价标准和合成正反例。不能预制后冒充客户事实的，是产品性能、用户动机、市场份额、活动优惠及客户引言。

品牌包建议包含：受众与情境、已确认定位、主张与证据、表达规则、渠道规则、可用资产、禁用内容。每条重要主张关联来源和适用范围；未知项保持未知，不因模板需要而补造。

同一个客户可同时有长期品牌规则、当前活动范围和本次局部要求。发生冲突时指出具体差异，不静默选择旧规则。用户改一封邮件，不意味着必须先重新建立完整品牌体系。

### 4.2 方法包：把理论转成“怎么做、何时不用、怎样检查”

定位、文案与 Slogan 不应合为一个巨大提示词。例如 April Dunford 将定位分为竞争替代、差异能力、客户价值、目标细分与市场类别，并明确定位不是一句 Tagline；Copyhackers 则把研究、信息层级、写作框架与编辑检查组织成工作过程。[S14][S15]

对 Mokina 的建议：

- 做受众与定位时，可以选择 STP、竞争替代分析等方法，但输出应是选择、理由、证据与取舍，而非只填框架表。
- 做 FABE / Message House 时，应用于合适的产品表达任务，不作为所有营销任务的上游门槛。
- 做文案时，根据受众认知、渠道与目标选方法；AIDA、PAS 等是组织工具，不是任何文案都必须完整出现的章节。
- 做 Slogan 时，基于已确认的核心承诺形成不同创意方向，说明表达理由，再检查具体性、可理解性、品牌关联和延展性；不让记忆性自评分替代真实传播效果。
- 做“解释”“缩短一句”“只分析数据”时，不自动运行完整 GTM 链。

### 4.3 成果蓝本：预制的是交付结构，不是固定答案

以 Email 为例，完整成果应支持：受众与触发条件、目标、主题、预览文本、正文、CTA、序列节奏、退出条件、分支、来源和指定导出版本。用户只要一封邮件时，提供单封结构；只有明确做序列时才展开序列逻辑。

“把所有邮件写得流畅”还不够。整套邮件是否重复、承诺是否一致、下一封是否接得上、用户已完成动作后是否应退出，同样属于交付质量。分支与发送策略设计不等于已经配置或发送。

这正是工作台相对裸 Skill 的价值：方法产出进入可编辑对象，而不是结束在一段 Markdown 回答里。

## 5. 质量：区分首稿一次可用与整套交付可用

建议直接使用已有项目中可授权的材料和审阅标准做质量回归，不新增需求访谈。客户原始资料不因用于内部项目就自动可公开为案例。

| 质量层次 | 判定方式 | 不应混淆 |
|---|---|---|
| 首稿一次可用 | 用户第一次收到的交付稿无需重写核心判断或主体结构，只有偏好性微调；允许产品内部已执行检查 | 不等于模型第一次原始输出就完美 |
| 整套交付质量 | 跨文档、邮件、渠道、图文的事实、主张、受众和行动一致；必需组成齐全、可读可改可交付 | 单篇高分不代表整套通过 |
| 精修质量 | 只改变指定内容，保留已确认部分；建议有理由、差异可查、候选可回退 | 不能把每次修改都做成整套重写 |
| 真实营销效果 | 有实际发布/发送后的数据才能评价 | 质量评审通过不等于点击、转化或品牌效果已提升 |

每种成果建立小而具体的检查表，不统一成一个“质量 95 分”：

- 可机械检查：必填字段、条目数、数值/公式、引用是否存在、未修改字段是否一致、导出是否匹配。
- 专业判断：受众取舍、论证强弱、语言质量、信息层级、品牌表达及内容之间的衔接。
- 需要保留意见的部分：创意偏好、未知市场响应、证据不足的策略推论。

现有研究支持“专业 Skill 可能带来实质改善”，但不是任何 Skill 都有效。SkillsBench v4（2026-06-14）报告，在 87 项任务、18 种模型与运行配置中，精心准备的 Skill 将平均通过率从 33.9% 提升至 50.5%；较精简的 Skill 组合优于过大的包。这是跨领域基准结果，不能把 +16.6 个百分点写成 Mokina 已实现的提升。[S16]

Mokina 可以用同一批既有案例比较“通用指令 / 方法包 / 方法包加质检”，看改善来自哪里。目的在于选择有效的专业资产，而非重做需求验证；不要求客户记录操作时长，也不以跑分代替最终稿审阅。

## 6. 技术与业务架构：学分层，不照搬全部复杂度

建议的逻辑关系如下；这是设计建议，不是当前实现：

```text
用户目标 + 本次材料 + 已确认品牌背景
                  ↓
任务识别 / 范围确认（允许直接编辑、只讨论、只分析）
                  ↓
选择主方法 + 成果蓝本 + 必要检查
                  ↓
冻结本次上下文与资源版本 → 调用既有 Agent / 工具
                  ↓
结构化成果 + 可编辑工作面 + 版本
                  ↓
具体问题检查 → 局部精修 → 用户选择
                  ↓
指定版本导出 / 选定内容接续 / 经确认保存可复用偏好
```

建议保留三个主要边界：

1. **专业资产层**：方法、品牌规范、示例、检查规则，可版本化和替换；不携带未经确认的外发动作。
2. **工作与成果层**：延续工作身份，管理计划、资料选择、成果版本、审阅与引用；不同方法不建立不同生命周期。
3. **执行适配层**：Agent 和工具负责真实执行；方法不假装有权限、连接器或数据。

Open Design 的桌面包使用 Electron，前端有 React 组件，daemon 与 contracts 等分包承接运行和接口；从技术方向上支持“专业资源与通用工作台分开维护”。但其上游同时存在旧提示词路径与 OD Next 策略路径，`composeSystemPrompt` 会分支；上游文档也记录了不同路径的差异。[S17]

因此若选 Open Design 为底座，应先确定本轮实际走的运行路径，保证营销规则、成果契约、导出和恢复都能到达该路径。不需要先重构上游全部架构，也不能只在一份提示词加上营销说明就宣告适配完成。

业务架构上，优先把自己的客户经验做成“品牌/项目配置 + 专业能力包 + 交付蓝本”。客户特例若不断回流到工作台核心分支，仍会变成定制项目集合；相反，稳定共性沉淀在默认能力，差异留在客户扩展，才形成可复制产品。

## 7. 市场流量：专业资产本身可以成为分发入口

### 7.1 已观察到的入口与信号

| 信号 | 本轮观察 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 开源关注 | GitHub API：Open Design 96,057 Stars；Marketing Skills 50,105 Stars；均为本轮快照 | 专业资源加 Agent 工具在开发者生态有可见关注 | 独立用户、营销人员占比、收入、留存 |
| 技能安装入口 | skills.sh 显示 Marketing Skills 4.8M 累计安装，copywriting 199.9K，copy-editing 125.2K，cold-email 107.9K | 存在“按具体任务找能力”的分发面 | 这些不是去重人数、活跃数或市场规模 |
| 规范/模板目录 | Open Design 把模板、Skill、设计体系分别做成公开详情页，并连接下载和贡献入口 | 内容资产既能使用，也能被发现和传播 | 无公开访问、安装和付费转化数据 |
| 商业承接 | Marketing Skills README 链接作者的服务和 Magister；Magister 有网页、Slack、MCP 与工作流详情页 | 不必先让用户换桌面应用，能力也能在已有工具里被发现 | 没有证据证明开源流量已高效转付费 |

来源：[S1][S8][S11][S12]。skills.sh 官方说明安装统计来自 CLI 的匿名安装遥测，并非运行数据。其目录显示 70 个技能条目，而本轮固定源码 `skills/**/SKILL.md` 为 50 个，目录还含旧名称条目；本轮没有逐项去重，不将两个口径混用。

### 7.2 建议的两条市场路径

**路径 A：已有企业项目向外复制。** 将已有客户项目中确实可复用、获准使用的工作整理成案例、合成示例和能力包；不因客户名称误读而假定其中包含邮件渠道项目。利用既有客户关系、营销服务商与专业内容渠道进入适配讨论。商业承接可以是标准产品加客户配置，不强制所有需求变成低价个人订阅。

**路径 B：开放专业能力形成自然发现。** 公开少量真正可用的 Skill、成果蓝本与合成案例，发布到适用的开源/技能目录；详情页直接给出输入、首稿、修订前后、交付版本和适用限制，再连接 Mokina 工作面。公开范围和发布许可另行决定，本轮不执行发布。

两条路径可共用同一能力包。不是先开一个大型插件市场，也不要求先做完整免费桌面发行版。MCP / Skill 是可选分发形态，不能因此在本轮研究中扩大到实现全部运行接入。

### 7.3 渠道优先级与适合提供的内容

| 优先级 | 入口 | 给用户看的东西 | 进入 Mokina 后的接续 |
|---|---|---|---|
| P0 | 既有客户与合作代理商网络 | 可授权的完整交付案例和可替换资料的演示 | 带本品牌规则完成相似工作 |
| P0 | 按任务搜索的中文/英文详情页 | “会员召回邮件序列”“GTM 信息主张表”“品牌 Slogan 精修”等完整范例 | 换入资料，编辑和导出，而非再读一篇文章 |
| P1 | GitHub / skills.sh / 适用的 Agent 插件目录 | 可独立使用的少量专业能力包、版本和样例 | 复杂成果进入工作台继续精修 |

数英官方定位覆盖广告营销从业者、品牌与机构；增长黑盒官方介绍覆盖消费、品牌营销和增长研究；PMA 有定位、GTM、竞争情报等专业内容和社区。这支持渠道受众匹配判断，不代表已合作或已取得流量。[S18][S19][S20]

本轮没有关键词工具、Search Console 或各站后台数据，不能报告关键词月搜索量、获客成本或渠道转化率。上述关键词是内容主题候选，不是搜索量排名。也不从 Stars 推断中国营销人员规模。

后续只需衡量真实可取得的数据：各入口带来的有效访问、案例打开、启动工作、完成可交付成果、回来做第二项工作，以及企业适配咨询。免费 Skill 的安装数与工作台活跃分开；本地产品不因需要增长分析而默认上传客户材料。

## 8. 重新组织竞争关系

- **Open Design**：最重要的业务/技术实践参照，也已有营销场景，并非完全不竞争。
- **Marketing Skills + Magister**：最接近“方法产品化 + 专业 Agent + 分发入口”的新重点；其开源库可参考，商业产品不可当作开源代码复用。
- **Anthropic Marketing Plugin**：既是方法和连接器组织的可复用候选，也是通用平台吸收专业能力的直接例子。
- **Jasper / Typeface**：仅保留上一版提及的商业产品背景；按本轮范围，不继续展开纯商业竞品研究，不纳入开源复用候选。
- **AionUi 等工作台**：可以复用基础能力，不必把 UI 壳与多模型支持当作必须自研的差异点。

结论不是“公开方法没有壁垒”，而是“公开方法是起点”。可积累的优势更可能来自：客户项目中提炼的可执行标准、经审阅的成果蓝本、失败案例与修复规则、中文及行业适配、跨成果一致性，以及这些内容稳定进入每次工作的能力。客户数据本身不因产生过就自动成为可跨客户复用的资产。

## 9. 建议的下一项产出，不新增需求调研任务

当前先抽象不同营销场景如何共用背景、工作、成果与方法，讨论 Mokina 的产品形态及其与通用 Agent 的关系。暂不选择首个渠道或交付样板，不启动质量对照；配套开源候选保留作设计参考。

此前“Email 首个质量样板”源于把伊美尔客户误读成邮件渠道，已撤回。网页版“社媒先行”同样不视为产品边界；质量目标继续保留，验证安排待产品形态明确后再讨论，不新增需求访谈。

然后才进入主线程决定：在 Open Design 哪一条实际运行路径上承载这些能力、先实现哪些成果编辑面、公开哪些能力作为分发资产。本轮不创建新应用、不修改主线程设计、不 Fork、不接模型、不发布或联系外部机构。
