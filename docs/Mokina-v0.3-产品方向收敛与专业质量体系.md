## 1. 收敛后的判断

**Mokina 应沿着 OpenDesign 的专业生产产品思路发展：复用工作台和运行能力，把建设重点放在专业营销方法、客户品牌规范、完整成果蓝本，以及交付前检查和交付后精修。**

这里的核心产物，不是“更多 Agent 功能”，而是营销人员第一次拿到就能进入正式工作、无须重建思路和大段重写的一套稿件。首稿可用性与整套成果质量是两个同时成立的要求，不能用其中一个代替另一个。

在产品形态和场景共同结构明确之后，可再分别考虑以下工作线；当前不以这些验证任务替代产品定义：

| 工作线 | 要解决的问题 | 判断依据 |
|---|---|---|
| 专业质量 | 同样的资料，能否更稳定地得到专业、完整、可继续修改的成果 | 既有项目 Brief 的首稿、成套交付和局部修改对照 |
| 开源底座适配 | OpenDesign 能否承载这些工作，哪些需要插件或宿主改动 | 同一任务的真实运行、保存、编辑、版本、引用和导出 |
| 市场触达 | 如何让更多有类似需求的人找到并使用 Mokina | 任务内容页、示例和能力包带来的有效访问、实际使用与业务线索 |

用户已有项目经验作为推进需求依据，不再安排需求访谈。高客单定制意愿说明存在有价值的问题，但不自动给出标准产品的价格、获客渠道或转化率；这些是不同的问题，不应以“重新验证需求”混在一起。

| 交互负担 | 简化计划、版本、采用和接续，不做六套管理系统 | 保留可靠性，减少必经确认；具体编辑/采用规则的简化仍是待写入下一版 Spec 的建议 |
| 下一步验证 | 找真实营销人员完成一次社媒工作 | 当前先做产品形态讨论，不新增访谈，也不把效果对照提前为下一步任务；质量及技术验证留待产品结构明确后安排 |

因此，这轮不是否定原有成果、版本与依据机制，而是调整主次：它们服务专业生产，不是产品价值的全部。

旧版“必须沿用 V6.2／美的外壳”的阶段约束不再作为本轮设计前提；当前方向是 Mokina 自有 UI，参考或复用 OpenDesign。原型中已积累的否定指令、局部修改、引用、恢复等行为案例仍可保留为回归要求。

## 3. 对 OpenDesign 的理解再推进一层

### 3.1 真正值得学的是“专业起点能够进入生产过程”

OpenDesign 的一个设计体系包，除 Token 外，还声明规范、组件、使用说明、预览及来源文件。这支持把专业知识组织成可维护资源，而不只是留在模型的通用知识里。[设计体系 manifest](https://github.com/nexu-io/open-design/blob/39d9eb593ba41037d1900e73f0e62489ef8ac5c1/design-systems/agentic/manifest.json)

对应到 Mokina，用户说的两块价值可以展开为：

1. **起点有质量**：已有品牌规范、方法和成果蓝本，减少遗漏、泛化表达和无效试探。
2. **过程能改善**：在真实成果上定位问题、提出修改、查看变化并继续交付，而不是每次重新生成整篇。
3. **体系能维护**：方法有版本，实际选用有记录，新的经验能进入下一次工作，而非散落在聊天记录中。

以上是产品设计推导，不是本轮测出的 OpenDesign 或 Mokina 质量提升。

### 3.2 “安装过”不等于“这一轮确实使用”

固定源码中的内置策略加载器读取明确声明的文件，绑定包及选定任务资源的摘要；重新加载与原绑定不一致时会报错。该实现限定于其内置策略，不能据此宣称所有第三方插件都具备同样机制。[策略包加载源码](https://github.com/nexu-io/open-design/blob/39d9eb593ba41037d1900e73f0e62489ef8ac5c1/apps/daemon/src/plugins/strategy-package.ts)

Mokina 应借鉴的要求是：可检查本次实际加载的方法、规则和资料版本。执行记录中的“已载入”只证明载入，不证明模型遵守、更不证明成果合格。

架构文档还说明 legacy、OD Next、daemon/API 等提示词路径存在分叉，并以共用成果协议说明如何防止规则只在部分路径生效。其“已知缺口”标注的是文档内较早核验日期，本轮不将它们全部当成当前未修复缺陷。[提示词组合文档](https://github.com/nexu-io/open-design/blob/39d9eb593ba41037d1900e73f0e62489ef8ac5c1/docs/prompt-composition.md)

由此得到的适配要求：先明确 Mokina 首版实际支持的运行路径；成果结构、版本和局部修改契约由宿主统一保证，专业方法通过能力包提供。不能只改一份提示词，就宣称所有入口完成营销适配。

### 3.3 精修值得学，虚拟评分剧场不必复制

固定版本的旧 Critique Theater 开关已被代码关闭；保留的质量检查 Skill 强调具体缺陷、修复和无收益时停止，并禁止虚构评委或评分剧本。它们分别是开关状态和方法文本，不能合并成“当前 UI 已完整运行自动评审”的结论。[关闭开关](https://github.com/nexu-io/open-design/blob/39d9eb593ba41037d1900e73f0e62489ef8ac5c1/apps/daemon/src/critique/rollout.ts#L104)，[检查方法](https://github.com/nexu-io/open-design/blob/39d9eb593ba41037d1900e73f0e62489ef8ac5c1/plugins/_official/atoms/critique-theater/SKILL.md)

Mokina 的精修界面应呈现“哪处有问题、影响什么、怎么改、改了什么”，不需要呈现几个虚构专家互相打分。

## 4. Marketing 专业体系：预制什么，分别放在哪里

不把所有资源统称为 Marketing Token。建议分成五类，但不意味着新增五个用户必须管理的模块。

| 资产 | 包含内容 | 对质量的作用 | 不能代替什么 |
|---|---|---|---|
| 品牌与表达规范 | 称谓、术语、语气及正反例、禁用表达、渠道表现规则 | 保持品牌感与表达一致，减少低级返工 | 客户真实产品事实 |
| 工作事实与证据 | 已确认受众、产品与服务事实、历史成果选段、数据、有效条件 | 避免虚构承诺，解释内容为何如此判断 | 策略选择和创意 |
| 专业方法包 | 研究问题分解、定位、GTM、Email、文案、Slogan、分析方法 | 提高判断和制作的专业起点 | 用户目标、实际执行授权 |
| 成果蓝本 | 好稿结构、可编辑字段、成套交付清单、示例与反例 | 从“能写文字”提升到“能交一套东西” | 这次工作真正需要的范围 |
| 检查与精修规则 | 事实、品牌、内容说服力、跨稿一致性、局部修改及导出检查 | 在交付前修问题，在交付后可控改进 | 人的最终审稿、真实市场效果 |

专业方法是可选择的推理与制作办法，不是每项工作都走的流程。例如已确认定位后写邮件，直接复用定位；只改主题，不重新研究市场；只分析 CSV，不自动启动内容制作。

### 4.1 经典理论应成为判断工具，不是固定填空题

定位与 Slogan 要分开。April Dunford 的原始说明将定位与传播表达区分，并强调竞争替代、差异能力、用户价值、目标客群和市场类别之间的关系。Mokina 可据此组织定位问题，不能用一句顺口的口号代替定位，也不必让已有定位的用户重填全部框架。[原始方法说明](https://www.aprildunford.com/post/an-introduction-to-positioning)

GTM、STP、AIDA、PAS、Message House、FABE 等可以进入方法目录，按问题选择。每个方法都应交代适用条件、所需证据、可产生的成果和不适用情况；“完整理论体系”不等于每次把所有理论串行执行。

### 4.2 开源 Skill 是候选原料，需要有编辑判断

这次补查带来三个明确的适配要求：

- Corey 的 `copy-editing` 可借鉴分维度精修，但它也包含虚拟专家评分门槛。保留具体检查，移除以模拟分数宣布合格的规则；其中补数字、增强紧迫感、增加保证等建议只能在客户事实允许时使用。[固定 Skill](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/skills/copy-editing/SKILL.md)
- `copywriting` 的评估用例覆盖任务分流和输出结构，也有“使用某种标题公式”的断言。后者适合检查方法遵循，不足以判断创意是否专业；不能把合规套公式当成好稿。[固定评估用例](https://github.com/coreyhaines31/marketingskills/blob/5b2c0007766c6a1cf1d53fd8fc73e979e0821022/skills/copywriting/evals/evals.json)
- Anthropic 的 `email-sequence` 可借鉴完整序列交付，但预设字符长度、时序和效果区间不能成为客户事实。模板流程图中的点击与转化关系也必须按本次目标重定义；若目标是完成预约，点击不能默认等于预约完成。[固定 Skill](https://github.com/anthropics/knowledge-work-plugins/blob/8f877b63d26c68c0c5528e82892fe32d016a8ddc/marketing/skills/email-sequence/SKILL.md)

因此，Mokina 应积累经过筛选、适配和案例验证的能力包，而不是原样安装最多的 Skill。公开方法、客户私有规则和项目资料分开；客户案例未经授权不变成跨客户的公共样例。

## 5. 能力候选，不作为首发顺序（更正）

前一份清单列出了较多 P0 候选，应理解为研究池，不是首版同时开发清单。撤回“先形成交付样板”的当前推进建议；先抽象各类工作、成果和方法如何在同一个产品中组织。

### 5.1 Email 仅保留为开源能力的结构示例

以下内容来自邮件类开源 Skill 的研究，不来自用户的伊美尔客户项目，不证明用户希望优先做邮件。保留它仅为说明一种专业成果可能包含什么，不作为下一步交付任务。

在未来确有邮件任务时，可能涉及：

- 简洁的受众与沟通方向；已有确定方向时直接引用，不额外产出长报告。
- 按 Brief 数量制作的邮件，包含主题、预览、正文、CTA 与必要的个性化字段说明。
- 对应的序列表：每封作用、接收条件、间隔、分支与结束条件；各项与正文一致。
- 关键主张与依据对应、未能确认的信息和交付说明。
- 可阅读、可逐条修改、可导出的完整内容包；本阶段不把它称为已经发送或上线。

此工作可以只加载品牌/事实背景、Email 制作方法、必要的质量检查；资料已足够时不额外调用市场研究。

### 5.2 候选能力覆盖，不指定先后顺序

| 能力类别 | 具体资产 | 可涉及的专业内容 |
|---|---|---|
| 表达与内容 | 品牌/事实背景、邮件或其他文案方法、编辑与检查 | 内容组织、语气、单件与成组关系 |
| 策略与创意 | 定位/核心主张，以及中文 Slogan/关键标题方法 | 方向比较、依据、品牌关联 |
| 编排与分析 | 社媒条目、数据分析与选定结论接续 | 结构化字段、口径、结论与后续工作的关系 |
| 研究与规划 | GTM、研究、渠道专门规则、内容分发方法 | 研究问题、行动建议和专业方法的适用范围 |

Slogan 方法应区别长期品牌口号、活动主题、产品标题和邮件主题，交付不同创意方向、表达理由与应用样例。中文读感、歧义、品牌关联和语境需要自有规则；当前没有确认一份可原样采用、覆盖中文全过程的开源包。

Agent Skills 的规范允许方法配合参考资料、资源和脚本按需组织，格式验证只证明包结构有效。本轮建议沿用适配宿主的现成格式，不新建 Skill 协议。[Agent Skills 规范](https://agentskills.io/specification)

## 6. 把“首稿一次可用”定义清楚

### 6.1 首稿不是第一段模型输出

首稿指用户第一次收到的完整交付版本。它可以经过内部查漏、核对和有限修复，但不能为了宣布“首稿成功”隐藏失败、无限重试，或把需要用户补大量内容的半成品算作完成。

对一个资料足够、范围明确的工作，建议用以下标准判断：

| 层次 | 合格含义 | 失败示例 |
|---|---|---|
| 基本可靠 | 无关键事实错误、虚构数据/承诺；必需字段及文件可用 | 没有优惠资料却编出折扣；正文与所选引用版本不符 |
| 专业首稿 | 目标、受众、信息层级与表达成立；只需偏好性微调 | 要重新确定主要受众、重写主线或大段内容才可交付 |
| 成套质量 | 单件合格，整包覆盖所需交付，各处相互一致 | 每封都通顺，但序列重复；表格与正文 CTA、时序或退出逻辑冲突 |
| 精修可靠 | 准确修改指定对象，不破坏未要求改变的内容和依赖 | 缩短第三封却改了优惠、其他邮件或发送条件 |

前两项中的关键错误不能被“文风很好”抵消。输入缺少关键事实时，可以交付标明缺口的方向稿，但不能标为完整可用稿；如何补齐与“是否有市场需求”无关。

### 6.2 对外少承诺，对内看真实结果

推荐记录三个质量结果：

1. **首稿可用**：在明确范围、输入足够的案例中，有多少首次交付只需偏好性微调；保留案例数与分母。
2. **成套通过**：有多少内容包同时满足单件质量、完整性与跨件一致性；不要把单篇平均分当整包通过率。
3. **精修改动准确**：指定改动是否完成，未指定部分是否保持，关联处是否得到必要提示。

早期样本少时直接报告“哪些案例通过、哪里要重写”，不包装成稳定百分比。不让用户专门打卡耗时或采用次数；利用已有审稿意见判断。模型检查结论、内部专业审阅、客户认可和上线效果分别记录。

同一套稿“内容专业可交付”不等于“真实转化一定更高”。后者需要实际投放/发送与业务结果，不能由自评分或开源模板中的基准数字代替。

## 7. 对 UI 和交互的直接影响

用户仍从目标和资料开始。推荐方法可以在输入旁或工作说明中简要展示，例如“将参考本品牌表达规范，制作会员召回序列”；不要求先在 Skill 市场选术语、填写完整项目档案。

成果出现后，对话与成果并排。整套交付通过现有文件/成果标签组织；邮件或排期同时支持条目和表格编辑，不把每个状态做成路由。计划只在多项工作或用户要求时展开。

“本次依据”里按需查看资料、品牌规则和实际使用的方法版本；历史成果固定来源与下一次选用分开。专业检查默认呈现重要问题及改动，不把长评审报告变成额外交付。

建议将版本与编辑进一步分层：

- 用户直接编辑：保存并可撤销，不要求每次采用。
- 明确范围的 AI 修改：可考虑应用后展示差异并允许撤销。
- 对照方向、大范围改写、基础版本过期：保留候选，由用户比较决定。
- 选择性接续：预览带走的内容和固定版本，再创建新工作；不自动继承整个项目目录。

第二条是吸收网页版建议后的**交互简化提案**，与旧原型“AI 修订统一为候选”的规则不同，尚未作为已批准实现。无论最后采用哪种方式，都不能静默覆盖旧稿、错配来源或用迟到结果覆盖新编辑。

能力库作为可发现、可解释、可维护的专业资源入口；普通用户不必操作底层理论目录，也不必为了改一句话进入另一套工作台。

## 8. 代码复用路线：向 OpenDesign 靠拢，但先确认改动落点

当前倾向是 OpenDesign 一个主底座，营销能力包尽量独立维护。用户允许直接改开源代码，因此无需为了形式上的独立坚持全新实现；但本轮没有决定 Fork 或证明它已能直接承载全部契约。

| 类别 | 当前建议 | 后续需要取得的证据 |
|---|---|---|
| 尽量保留 | 工作区、对话与成果并排、文件工作面、基础运行与插件管理的合适部分 | 按实际版本运行，确认一般营销讨论不被设计向导阻断 |
| 调整后复用 | 内容包与资源选择、成果渲染、版本及局部编辑、专业检查 | 普通文档和结构化成果可保存、修改、比较、导出 |
| 检查后补齐 | 条目身份、选定版本引用、跨成果一致性、取消恢复、客户规则范围 | 不预判缺失；已有能力符合就复用，不符合再列宿主补丁 |
| 首版不引入 | 两套运行/存储系统、所有模型底座、虚拟评委剧场、强制全流程、全渠道自动发布 | 不把无关复杂度带入营销生产 |

选择顺序建议：

1. 先检查现有配置、Skill、插件与编辑接口能完成多少，不先改宿主。
2. 能满足核心行为则使用扩展；只差少量清晰的工作面/契约时，采用小幅 Fork。
3. 若普通文档和条目修改需重写主要运行、存储及编辑机制，再比较抽取模块或 AionUi 等替代路径；不因 OpenDesign 功能多就接受深度耦合。

底座适配与能力内容设计属于后续工作。当前先明确共同对象和界面关系；此后专业规则保持可移植，技术检查再选代表性工作，不默认以邮件样板作为入口。

## 9. 后续验证思路（暂缓，不是当前任务）

本节保留质量与技术验证的方法参考。用户已明确当前先考虑产品形态，不在本轮选择样板、运行对照或进行效果评价。

### 9.1 用已有案例做质量对照

待产品形态明确后，再按实际场景选择代表性 Brief，不预设邮件优先。只使用获准处理的历史资料或合成资料；历史定稿及审稿意见可以作为参考，不当成唯一正确措辞。

对照必须使用相同资料、模型版本、可用工具、工作范围及可比执行预算。通用提示词基线要认真编写，不能故意用一句弱提示词衬托 Skill。

| 条件 | 制作方式 | 是否安排独立检查 |
|---|---|---|
| A | 合理的通用任务说明 | 否 |
| B | 相同任务说明 + 经适配的专业能力包 | 否 |
| C | 合理的通用任务说明 | 是，给予与 D 可比的检查资源 |
| D | 相同任务说明 + 经适配的专业能力包 | 是 |

A/B、C/D 用于看专业方法的增量；A/C、B/D 用于看增加检查步骤的影响。若 D 使用更多推理资源，需单独说明，不能全部归功于方法包。成稿对照尽量不显示所属条件，沿用已有专业审稿标准；没有人工审阅时，不能把机械检查通过当专业首稿通过。

SkillsBench v4 报告了跨领域的配对提升，并指出聚焦的能力包表现优于庞大包；这支持采用对照方法，不提供 Mokina 的预期提升值，也不能外推为营销质量已验证。[研究原文](https://arxiv.org/abs/2602.12670v4)

### 9.2 同一个样板检查技术承载能力

在候选底座中完成资料载入、实际调用、首稿保存、第三封局部改写、手工并发编辑、历史版本查看、选择性接续、导出与重开。检查运行记录是否匹配所选方法与依据，下载内容是否匹配指定版本。

若质量对照差，先定位方法、资料或检查规则；若内容质量好但保存/精修/引用不可靠，问题在底座适配。不能用其中一条通过宣布另一条完成。

### 9.3 不用固定模板作弊

同样方法还要覆盖已确认定位、禁止折扣、只改一句、资料不足、客户品牌变化等变体。结果应随输入真实改变；缺资料时保留缺口，不用示例补成“成功”。

这些是产品质量与执行验证，不是需求访谈，也不是在提出新的实施前置审批流程。本轮未执行上述对照。

## 10. 市场流量：让专业资产成为可体验的入口

继续以既有客户及合作网络为最直接的首批触达来源；增量市场优先围绕具体任务展示可用成果，而不是泛泛宣传“全能营销 Agent”。

建议一个专业资产提供三个互相一致的形态：

- 产品内：可替换资料、继续修改的能力与成果蓝本。
- 对外示例：合成或获准公开的 Brief、完整首稿、精修前后及修改理由。
- 开源候选：可独立使用的少量方法包和用例，明确版本与适用范围。

公开资产不应只能看一张漂亮截图；要让读者判断“这是否接近我实际要交付的东西”。但不要为了导流，把开源 Skill 做成不能独立使用的空壳。

GitHub、Skill 目录与面向营销任务的内容页各有入口价值，但尚无本项目的渠道转化数据。skills.sh 官方说明其排名来自安装遥测，这不代表技能已执行、稿件可用或用户愿意使用工作台。[官方统计口径](https://www.skills.sh/docs)

后续分别观察内容入口访问、示例使用、带自有资料开始工作、可用成果及后续业务线索。客户咨询和标准产品使用可以是两条出口，不假设所有企业定制客户都会转成同一种订阅用户。

本轮不扩展纯商业竞品研究，不发布资产、不进行投放、不联系客户。是否公开具体方法和案例，留待资产范围明确后决定。

## 11. 下一步的具体产出建议

当前撤回“先做专业交付样板，再把能力映射到 UI”的推进顺序。先讨论三个相互关联的问题：

1. **场景如何统一**：研究、策略、内容、编排和分析各自有什么对象与操作，哪些机制共用，哪些表现必须保留区别。
2. **产品是什么样**：目标输入、营销背景、持续对话、成果工作面和专业方法，在同一个工作区中如何出现和切换。
3. **专业性落在哪里**：学习 OpenDesign 怎样把专业资源和成果操作组织成默认工作环境，而不是仅列出比通用 Agent 多了哪些功能。

这里记录本轮问题范围，不将新的场景优先级、UI 布局或 Fork 路线标为已确认。首稿质量与整体交付质量保留为后续设计和实现的目标。
