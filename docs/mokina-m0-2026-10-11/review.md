# M0 缺陷优先审查

审查基线：`98851a978840ef84a649379cfe3fa86cb63a8212` 之后的本轮改动。实施者与审查者交叉检查；不是仅检查测试数量。

| 发现 | 用户影响 | 处理与验证 |
|---|---|---|
| P07 localStorage 读取失败后，异步 flush 再次读取可能抛异常；版本选择也直接读存储 | 存储受限时空草稿/未处理异常，甚至妨碍版本浏览 | 增加独立读取失败状态与显式重试；版本浏览保留。R01 已补回归 |
| 迁移递归重写所有 JSON 路径字段 | 冻结来源的摘要与原内容不再匹配 | 收窄为明确可变的运行时指针；固定快照、版本、请求与原生恢复字节保留。R04 集成验证 |
| tools-pack 在宿主迁移选择前创建目标 profile 中的配置/日志目录 | 首次启动被当成“已有 profile”，跳过迁移入口 | 工具启动准备记录移到工具拥有的输出路径；不放宽禁止覆盖目标的规则。R04 验证 |
| 恢复包只检查版本 parent/base 引用存在，没有识别循环/重复序号；容量未给清单预留条目 | 损坏关系可能被标完整，边界包可能无法导入 | R02 同时校验导出/导入图关系与容量，明确缺失原因 |
| 导入草稿身份在 await 前绑定 A workspace，发送时重新读取 B workspace | 导入被提交到错误空间，旧响应还能抢走当前导航 | 固定调用开始时的 scope；发送前复核；完成后仅更新同 scope UI。R02 回归 |
| 前次恢复成功提示和失败报告可同时出现 | 用户难以判断本次是否完整成功 | 新操作清理旧通知，workspace 切换清理旧报告/执行入口。R02 回归 |
| 外部文件夹项目只从工作文件根收集恢复包 | 历史与固定来源存在于 managed store，却被遗漏后标为完整 | 真实 daemon API 红例已复现；原件与受管理历史分别读取，统一验证完整性 |
| 900 像素宽时侧栏保留展开状态却被设为不可点击 | 恢复导出和导入入口不可达 | 同尺寸红例已保留；补 Mokina 范围的打开态布局，不变更通用宿主规则 |
| 原生迁移选择等待 ready，随后才设置 sessionData 路径 | 第一次启动可能提前使用默认 Chromium 数据位置 | 独立 Electron 探针确认 ready 会创建目录；复用原有 launcher→受管代际边界隔离引导会话 |
| 迁移恢复记录校验弱于实际 recovery store | 报告已保留的记录随后不可读取 | 对齐实际 schema、recordId 与删除墓碑校验 |

最终结果和具体测试以 [README](./README.md) 及各项证据为准；本表记录问题与修复理由，不独立构成通过结论。
