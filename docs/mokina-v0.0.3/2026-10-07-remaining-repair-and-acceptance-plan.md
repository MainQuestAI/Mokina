目标：让本地通过结果与远端检查对应到明确 head，而不是以推送成功代替 CI。

1. 在开始修复前再次核对 worktree、分支、head、remote 与现有 PR，保留未跟踪资料；不预定 PR 编号。
2. 对当前已推送分支手动执行既有 `ci.yml` 的 workflow_dispatch；不为运行 CI 创建无关 PR，也不扩大 push 触发器。命令为 `gh workflow run ci.yml --repo MainQuestAI/Mokina --ref codex/mokina-v003-repair-a-input`。
3. 保存实际 run URL、head SHA、命令、结论与失败日志。run 被跳过、取消、排队或 dispatch 失败均不记通过。
4. 若失败，对照同基线和本地环境，修相关故障；保留原失败，不 blanket skip、不用增加 timeout 隐藏挂起。远端默认分支未登记 workflow 时先说明具体限制，不用未授权 PR/合并绕过。

完成条件：已有新增/受影响集合在目标 SHA 上得到实际远端结果；未解释的新回归为零。后续运行代码变化仍需对应 head 的检查，不能沿用这一轮 CI 结论。

### R2：补齐旧记录升级与可信窗口验证

目标：升级后仍能找回未发送内容；同项目不同会话、同 profile 不同可信窗口不串资料、不互删新记录。

**升级输入**

- 从受保护的旧配置副本同时取得 daemon 数据与 Electron 恢复存储/旧界面缓存。沿用根 AGENTS.md 的 Daemon data directory contract 和既有 tools-pack namespace，不另造数据根。
- 记录旧包版本、源码、备份摘要、项目/会话/快照/版本计数、恢复 key/recordId 与记录版本。原配置不就地升级，不把凭据、客户文件或完整 profile 放进公开仓库。
- 如真实旧 profile 暂不可得，可在隔离的旧候选中通过正式入口创建合成草稿、project-only pending、unknown send 和 v2 journal，再升级。该结果只证明代表性兼容性，真实历史配置仍标待验。

**必须覆盖**

1. 能证明会话归属的旧 pending 迁移后只由对应会话领取；无法判断的保留并提示确认，拒绝确认不删除原件。
2. 已消费墓碑与迟到旧 localStorage 同时存在时，不复活旧资料；schema 1 快照正文/指纹不重算。
3. v2 journal 有匹配目标文件/快照时复用目标；缺完整意图且目标不足时停止，不猜选择、不换 target、不自动发送。
4. 升级期间出现读取失败、CAS 冲突、损坏记录时显示可恢复错误；允许重试/备份，不以空记录继续运行。
5. 同一 profile 的两可信业务窗口：A 固定输入并提交，B 更新为新 generation；A 迟到清理不得删除 B。另一会话不得读取 A；unknown 使用原 requestId 查询。窗口重开后与权威记录一致。

**代码核查方向，而非已确认缺陷**

当前 `apps/desktop/src/main/runtime.ts` 的恢复 IPC 只接受主窗口 webContents；存储实例在该初始化中创建。先确认现有宿主是否提供第二可信业务窗口，并验证两窗口 handler 注册、store 实例归属与读写路径。不能把 artifact 预览窗口当作业务窗口，也不能删掉 sender 校验让全部窗口调用存储。

若复现多窗口失败，最小修复方向为同一 main/profile 持有一个权威 store、IPC 校验明确登记的可信业务 renderer、关闭窗口后注销身份；Web 仍用现有按键队列/CAS 和 generation 校验发布缓存。子窗口、iframe 和外部页面必须继续被拒绝。若宿主根本没有第二业务窗口入口，先报告能力缺口；新增窗口能力需另行确认，不隐含在本方案内。

主要模块：desktop 的 `runtime.ts`/`mokina-recovery-store.ts`，Web 的 `runtime/persistence/mokina-recovery-store.ts`、pending、send-request-state 与恢复提示。先在窄层复现，再运行真实 IPC/原生窗口，不用两个纯 JS mock 冒充原生验证。

完成条件：旧稿/旧记录保留，归属正确，重复模型运行和错误消费均为零；不受信任 sender 仍被拒绝。双不同 namespace 不等于同 profile 双窗口。

### R3：原生中断、响应丢失与源删除

目标：每个副作用中断后都恢复原 operation/target/snapshot，不丢草稿、不重复上传或运行。

复用既有 tools-dev/E2E 隔离机制和 tools-pack 生命周期。请求延迟/断连在测试层控制；不加产品“验收后门”或另一套进程框架。原生中途退出只作用于已核对的本次 QA 实例，旧应用不动。无法稳定命中的断点保留未跑，不靠 sleep 猜位置。

| 断点 | 中断后的操作 | 必须断言的用户结果 |
|---|---|---|
| prepared 已保存，创建目标前 | 退出重开并恢复 | 原 IDs；只创建一个目标；恢复不自动运行 |
| 创建目标服务端已成功，回执丢失 | 用原 target 查询后恢复 | 不第二次创建，不换项目 |
| 素材目标路径已分配，复制前 | 重开继续 | 稳定 inputId/目标真实 path；缺源明确报缺口 |
| 素材已复制，回执丢失 | 核对目标摘要，再删除隔离测试源 | 复用目标字节，不重复传，不读已删源 |
| 快照已固定，回执或 journal 更新丢失 | 删除隔离源章节/品牌/素材后恢复 | 读原目标快照；正文/指纹不变 |
| 接续文件已写，读回失败 | 重开并读回已有稿 | 同 operation；冲突不覆盖用户编辑 |
| binding 已持久化，界面缓存尚未发布 | 重开 hydrate | 完整草稿和正确会话绑定；不自动发送 |
| completed 已保存，活动 journal 清理失败 | 重试状态同步 | 不再次创建、不清除新 operation、不抢导航 |
| run 已受理，发送响应未知 | 按原 requestId 查询 | 一个逻辑运行；不另发模型请求 |
| run 已受理，pending 条件消费失败 | 只重试清理 | “已提交，待同步”；模型不重跑 |

补充失败场景：403、字符串/结构化/非 JSON 错误、目标列表读取失败、目标草稿被用户改动、源从未复制就丢失、全部输入不可用。全部失败不进入成功态；明确排除/修改选区必须确认新副本，原记录仍可恢复。

主要模块：`continuation-recovery.ts`、FileViewer、ProjectView、pending/send-request-state。每个发现先保留 red case，再最小修复，更新同编号回归。断点工程自动化全部通过与原生实跑分别登记，不重复铺满昂贵 E2E。

完成条件：所有身份保持、内容摘要匹配；已受理的运行仅查询/同步，不重发；两侧用户编辑保留。源 LOGO 删除后，目标依据与交付仍从已固定资源读取。

### R4：导出问题收尾及应用外打开

目标：完整版本能离线交付；资源不足的旧历史稿能理解失败原因，并有不会混版的恢复路径。

**历史资源不足的明确处理**

1. 保留历史导出禁止读取当前资源的现有规则，不为让 v1 通过而补造历史 frozenContent、回填旧指纹或读取今天的 LOGO。
2. 在 `import-export-routes.ts` 与既有 Web 导出错误处理统一“该历史版本缺少自身保存的资源，不能完整导出”及已知缺失项。必要时沿现有结构化错误形状补一个明确错误码，放入 contracts，并由 HTML/ZIP/PDF 与 CLI 共用。
3. 仅缺少 frozenContent 不构成拒绝条件：自包含的旧正文仍可导出。只有实际未满足的依赖或外部资源需要明确阻止，避免扩大故障。
4. 提供/复用显式“恢复为新版本后再导出”入口。用户确认后才产生新版本并固定当前可用资源；明示这是新版本，不是修好了旧历史稿。原历史稿和未采用候选保留；若资源依然缺失，继续显示缺口。
5. 补测试：旧稿自包含可导出；旧稿缺资源明确失败；当前资源不同不能混入；恢复后新版本可导出；取消无文件/无成功提示/无版本指针改变。文案改动运行 i18n 检查。

**应用外验证**

- 对同一候选的 current/historical/candidate × HTML/ZIP/PDF 九份核对内容、版本 ID、资源与摘要；HTML 和 ZIP 解压后的 index.html 由用户手动在应用外打开，并记录实际浏览器/版本、结果与截图。
- 本次 Chrome 工具明确拒绝 file 协议且禁止绕过；后续不改浏览器、不搭本地服务来规避该限制。用户手动操作完成才补记通过，静态解析不替代这一步。
- PDF 已验证图像型输出。滚动条入图作为交付质量观察保留，先核对与输出有关的容器/样式；若确认需要修复，只影响导出渲染，不改变原页面可滚动性。不顺带承诺可搜索文字 PDF 或新排版引擎。

完成条件：三种完整版本九份实际文件均与所选身份一致、资源可读；历史不足项明确失败且可保留原稿恢复；应用外打开与取消分别有真实结果。

### R5：固定新候选，补齐完整原生与业务链路

R1–R4 的产品变更稳定后固定 source SHA，再构建一个新候选。版本暂定 `0.0.3-local.6`，构建前核对登记；不得与已签收的 `0.0.2-local.6` 混用。只有文档变化时说明 source/validation 差异，不因字符串不同重复打功能相同的包。

所有以下必需项在同一包完成。中途改运行代码/资源则产生新候选，重跑受影响项及必要公共链路，不拼接多个包的验收。

1. **干净配置**：源码目录外安装、首次连接、原生文件选择、普通文字直发、CSV 精确选择/固定/提交/独立计算、中文输入、退出重开。
2. **升级配置**：完整受保护旧 profile，历史项目/版本/候选/快照及 R2 的旧 pending/journal；升级前后摘要与身份比对，保留旧包和回退副本。
3. **可信窗口/恢复**：R2/R3 原生适用项；真实授权不足时保留具体未跑项，不用 mock 权限代替真实 workspace 验收。
4. **业务品牌 A→B**：读取 A 后切 B，B 读取中不能固定旧 A；只选定规则/素材进入目标，SOURCE_CHANGED 重读再确认；A 旧快照摘要不变。沿正确 workspace/project 获取 run 与 snapshot，不显示上一身份数据。
5. **接续下游成果**：从历史/候选选定章节、品牌和单一素材，创建可编辑草稿；修改选择确认新副本；用户明确发送后再生成目标成果。检查不夹带未选章节、实际固定规则/素材与成果一致，原项目/目标稿/完成记录不丢。已有 fixed 目标不依赖已删除的测试源。
6. **交付**：R4 九导出、取消、正式恢复 ZIP 的 manifest/全成员摘要与正式导入；不只检查文件存在，不用导入标记代替 ZIP。
7. **连续使用**：冷启动、首开接续、切版本、返回成果；1280×720 与 1440×900 原生发送/恢复/版本/接续/导出入口可达。原白屏仍遵守“无法复现先跳过”，不因正常打开改为已修复。

真实业务品牌需要两份可用于此验收的 A/B 规则、各自 LOGO/素材、禁止事项及冲突时的优先级。数据仅进入受保护验收环境；进入外部模型前确认允许的资料和模型目的地，客户原件不加入公共夹具/截图/PR。没有这些输入时，工程可以继续，T33 业务验收保持待资料。

完成条件：同一候选通过所有适用的必需原生链路，并记录源 SHA、验证 SHA、资源清单、包摘要、CI run、安装版本、完整成果和未跑项。不以 professional 待评补成工程通过，也不以工程通过补成用户签收。

### R6：专业评审与独立签收

复用已保存的两预算完整成果作初次专业评审，不为获取一句评语重复调用模型。若专业评语提出产品偏差，再由具体失败输入/结果制定针对性修复；不先重写营销提示或增加新引擎。

- **算术**：独立复算总额、百分比、CSV 数值；禁投项目金额为零，不允许改名后转支出。
- **可执行性**：渠道动作与预算逐项对应，缺门店容量/档期/单位等事实明确待确认，不虚构来源、ROI 或转化承诺。
- **品牌与资料忠实性**：使用确实选入的规则和素材，专业判断不得混用“已传输”与“模型已采纳”；依据与完整成果一起评。
- **差异判断**：两预算和额外禁投条件应改变执行取舍，而不只改表格数字。
- **签收**：每份成果保存专业意见、需改问题和用户结论；不代替用户作批准，不把空评语登记为通过。

若评审需要改变 Prompt，先阅读现有 prompt-composition 约定，核对实际 run 所用 legacy/OD Next 分支，只修对应契约；提示变化也需固定新候选与受影响成果复验。没有具体问题不预先修改提示。

## 4. 暂时跳过与独立治理事项

卡加载/白屏按用户明确要求保持「未复现，暂时跳过」。只有出现新的可复现项目/版本/请求与组件状态证据时重新打开 D1；不得用自动 reload、无限重试、单纯增加 timeout 或模型耗时猜测来关闭。

既有公开研究资料/本机路径继续按可公开、需脱敏、授权待确认盘点。当前树脱敏、删除、历史重写都需要明确目标与另行决定；本方案不自动删历史，也不阻断独立功能修复。未签名、公证、Windows/Linux、自动更新和 RAG 不列为本轮欠账。

## 5. 回归、证据与收口

每个实际修复切片同步代码/契约、red→green 或明确没有 red 的原因、受影响测试、UI 恢复路径与 F/T/AC 对照。沿用 Node 24/pnpm 10.33.2、实际 SQLite 和既有 CI 集合；guard、typecheck、受影响包测试必跑，UI 文案改动加 i18n。测试按现有 test-efficiency 约定等待业务完成信号、使用受控 promise，不靠固定 sleep。

证据记录至少包含：问题与用户结果、环境/profile来源、source/validation SHA、候选版本/包摘要、请求与 operation/target/snapshot/generation 身份、修复前失败、修复后结果、原生或 mock 的层级、专业评语/签收、剩余状态。公开仓库只放合成或已获公开授权的材料；完整 profile、客户原件与凭据保持私有。

收口采用四个独立状态：

- **功能工程**：A/B/C 与后续确证故障无未解释新回归，远端 CI 有对应 head 的实际结果。
- **原生候选**：同一包完成全部适用必需链路；无具体输入/工具限制的项仍明确待验，不按比例折算。
- **安全处置**：包内风险有逐项结论，未处置告警不以功能通过消除。
- **专业/用户**：分别记录人工评语和明确签收，空值保持待评/待签。

D1 的原根因关闭不再作为当前执行的前置，因为用户允许无法复现先跳过；但原故障状态继续开放。最终表述应为「除用户同意暂跳的 D1 外，已完成的工程/原生范围……」，不得宣称全部原 31 AC 无例外通过。
