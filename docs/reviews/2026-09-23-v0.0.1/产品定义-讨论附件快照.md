## 1. 产品定义

**Mokina 是面向营销人员、以项目和成果交付物为中心的开源 Agent 工作区。产品弱化会话概念，以 HTML 作为统一的成果呈现与操作载体，通过基于营销理论或业务流程的 Skill 及其 reference 模板，支持用户持续形成、修改和交付专业营销成果。**

保留面向个人使用者的 To C 开源定位。用户可以从市场问题开始，也可以带着品牌背景、产品事实、目标和 KPI 开展工作；不要求先完成复杂的项目配置或准备齐全资料。

### 1.1 项目与交付物优先，弱化会话概念

项目组织共同目标、背景、资料及相关交付物。用户进入项目，优先找到已有成果、当前进展和需要继续处理的内容；打开具体交付物，即可阅读、直接编辑、要求 Agent 补充或修订，以及基于选定内容继续后续工作。

会话保留为讨论、澄清、执行与追溯的基础能力，关联到所属项目及相关交付物。用户不必先定位某段聊天才能找到成果，也不必整理聊天记录才能交付。弱化会话不等于删除会话、并行运行或历史记录；具体入口和布局在 OpenDesign 原界面上逐块确定，不预设另一套独立工作台。

### 1.2 一切皆 HTML：统一成果体验

营销成果以丰富的 HTML 模板呈现和操作，不以 Word、PDF 等文档文件作为产品内的主要交付物界面。HTML 同时支持完整阅读、图表与矩阵表达、来源查看，以及适合该类成果的局部修改和后续操作；不能只是将长篇文字放进网页。

| 交付物示例 | 适合的 HTML 表达 |
|---|---|
| 市场与竞品研究 | 对比矩阵、定位图、研究结论和可展开的依据 |
| 品牌定位与策略 | 人群、需求、价值主张的对应关系，以及选择依据 |
| 营销活动方案 | 创意呈现、渠道分工、预算与目标之间的关联 |
| 执行计划 | 时间线、责任分工、里程碑与交付安排 |
| 复盘报告 | 指标对照、归因分析、局限与后续行动 |

上述是产品表达示例，不代表首版同时实现全部类型。HTML 可以包含图片、视频等内容；上传资料仍可保留 PDF、Excel 等原格式，对外需要时可从指定成果版本导出相应格式，具体支持范围另行确定。

HTML 是统一成果入口，同时保留支撑它的数据、来源、版本与引用关系，使局部修订、图表更新和跨成果接续有明确依据。不能只留下无法追溯的页面，也不要求用户直接编辑 HTML 源码。

### 1.3 Skill 与 reference：专业方法和呈现结构共同定义成果

各类型 Skill 按营销理论或业务流程组织，reference 承载对应的 HTML 模板、结构说明及必要示例。模板是专业方法的可视化载体，既定义怎样呈现，也帮助明确怎样完成这项营销工作。

每类 Skill 及其 reference 应共同说明：

- 适用的问题、所需输入，以及缺少信息时如何追问或标注缺口。
- 采用的营销理论或业务步骤，以及需要形成的判断与取舍。
- 结论需要哪些依据，如何区分事实、推断和假设。
- HTML 成果的内容结构、可视化表达和必要操作。
- 成果完整性与专业质量的检查要求。

例如，STP 模板应呈现市场细分、目标选择、定位及其依据和取舍，而不只是三个待填标题。模板允许按行业、品牌和当前问题调整，不强制每项任务套用所有理论，也不以填满模板代替专业判断。

### 1.4 围绕交付物接续工作

交付物可以独立完成，也可以作为下一项工作的依据。例如“市场研究 → 定位策略 → 活动方案”可以构成一条工作链，但不强制用户从研究开始或走完全部步骤。接续时保留选定内容、来源与版本；上游后续修改不静默覆盖已经形成的下游成果。

### 1.5 OpenDesign 底座与调整原则

以完整 OpenDesign 产品为底座，在其现有界面、项目、会话、运行和成果能力上优先增加营销能力，再逐块讨论明确需要减除的功能。每块回答“现在有什么、必须加什么、明确减什么”；未讨论的功能默认保留。登录等仅作为待讨论的减法示例，不因被提及就视为已批准删除。

已建立的独立 `/mokina` 前端不再作为主方向继续扩建。围绕项目和交付物调整交互优先级，不等于重建整个前端；已有资料解析、局部修订、版本和导出能力按原产品入口整合。

## 2. 已确认，不再反复讨论的决定

| 决定 | 对设计与实现的影响 |
|---|---|
| To C、开源，服务营销专业工作 | 不以企业采购、定制客户验收或额外需求访谈作为推进前提；伊美尔是客户，不是 Email 渠道 |
| 直接提出目标即可开始 | 不强制建项目、Brand Kit 或完整计划；长期背景按需建立、确认和复用 |
| 品牌背景、个人偏好、当前任务要求分开 | 一次任务的调整不自动成为永久品牌规则；搜索发现不直接当作已确认事实 |
| 第一期以逐步长成的协作为主 | Ask／Plan／执行区分行动意图，不是必须依次走完的流程；下一步建议先填入可编辑请求，由用户发送 |
| 会话并行是基础使用方式 | 左侧可切换工作，中间持续对话，右侧呈现成果；后台结果不能抢占另一个工作的画布 |
| 专业内核由方法、行业视角与能力组合支撑 | Skill、提示词和模板可以承担不同部分，不把每个概念都做成独立管理系统 |
| 研究可独立完成，也可为策略积累上下文 | 搜索不是必经步骤；已有资料、品牌故事、产品事实或内部 KPI 都可以成为起点 |
| 策略需要 KPI 拆解与具体判断 | 不纠结 KPI 是谁设定；结合预算、周期、主题与市场条件形成路径，缺项明确标注，不机械分摊数字 |
| 策略核心成果是可操作的营销方案 | 报告是同一成果的阅读与交付视图；支持局部编辑、候选比较、版本回看和选择性接续 |
| 可以直接复用 OpenDesign 等开源实现 | 不为差异化重造工作台；优先检查复用能力，但尚未决定 Fork 或采用哪个底座 |

## 3. 建议的首版范围

以下是待批准的首版建议，不把原型里出现的所有功能都升级为首版承诺。批准确定产品目标、首版能力边界及关键行为；技术核验细化实现，能力删减或关键行为变更须再次决策。

### 一条工作链，两个自然入口

- **问题入口**：提出市场问题，明确必要口径，形成有来源、有行业视角的分析报告。用户可以到此结束，也可以选择结论继续工作。
- **任务入口**：直接提供品牌、产品和目标／KPI，形成初步 Brief；按需研究和追问，讨论方向，再制作营销方案。

两者汇入同一工作区：背景与目标 → 讨论／必要规划 → 成果 → 局部修订与比较 → 同版本报告 → 按需带着选定内容继续。不是每项工作都必须走完整条链。

### 最小成果与专业能力

| 首版建议 | 最小可用边界 |
|---|---|
| 市场／营销分析报告 | 可调整问题、维度和口径，区分事实、推断与局限；来源可回看，不以搜索摘要拼接代替分析 |
| 可操作的营销方案 | 连接目标、KPI 判断、方向、行动及验证建议；允许 A/B 或组合方向，不强制三个方案 |
| Brief 与普通文档 | 作为工作过程和未专门支持类型的承载方式，不另建一套系统 |
| 品牌与任务背景 | 支持确认、修改和复用必要背景；没有 Brand Kit 也能开始 |
| 小规模营销能力包 | 先覆盖背景理解、按需分析、KPI／策略推导、报告组织和局部精修；不要求每次都运行全部方法 |
| 版本、引用和真实交付 | 手动编辑与 Agent 修改共用成果；保存恢复、指定版本导出、固定引用可靠，不把每次编辑变成审批 |

内容、排期、图片和视频是后续可接入的成果类型，不将首版限定为内容工厂，也不承诺第一版实现所有专用编辑器。

### 暂不纳入首版主线

项目看板与复杂 Agent 编排、全链路投放发布、完整视频制作、自动安装 Skill 的雷达／市场、多底座统一平台，以及企业权限与审批体系。保留扩展可能，但不以它们阻断第一条真实工作链。

## 5. 获批准后的下一步建议：核验复用路线

本文获批准并完成交接后，建议下一份产物是**技术复用结论与最小真实闭环实施方案**，不是新一轮泛竞品研究，也不是再次验证用户是否需要这个产品。当前不启动该阶段。

优先核验 OpenDesign，以固定源码版本和实际运行结果回答：

1. 现有工作区、会话、运行、成果和版本机制可以原样保留哪些；许可证对修改及分发有什么实际要求。
2. 用已有配置、Skill、插件和模板，能否接入营销背景、分析与策略工作；需要修改宿主的具体位置是什么。
3. 普通报告与策略成果能否被局部编辑、保存、比较和指定版本导出；引用是否能固定到选定内容与版本。
4. 切换会话、后台完成、取消及恢复是否满足已确认交互；哪些来自宿主，哪些需要补齐。

用同一个小任务检查：带入已有分析与品牌／KPI 背景 → 讨论并生成策略 → 修改一段 → 查看旧版与新版报告 → 选定结论另开工作。另行检查研究入口能否真实取得和呈现来源，不强制把搜索塞入已有充分资料的任务。

| 路线 | 采用条件 |
|---|---|
| 配置／插件扩展 | 现有扩展点足够承载核心交互与数据行为，无须绕开宿主机制 |
| 有限 Fork | 宿主大部分适用，必要改动位置清晰，能够隔离营销适配并持续维护 |
| 独立实现、复用合适模块 | 核心成果或运行方式存在结构性冲突，前两条路线经检查确实不合适 |

目前只有“优先检查 OpenDesign”的倾向，没有底座选型结论。不拼接两套相互竞争的会话、存储和运行系统。

## 6. 从原型进入真实首版的完成标准

- 用户自己的资料和要求真正影响分析与策略，未知信息和证据局限被保留。
- 品牌约束、专业方法与行业维度在结果中发挥作用，而非只出现在提示文案里；真实样例的质量仍需检查。
- 修改指定部分时，未要求改变的内容保持不变；原版可回看，阅读报告与导出对应明确版本。
- 选择性接续只带入指定内容与必要背景，来源后续修改不静默改写旧引用。
- 工作切换、后台完成、保存恢复和实际文件交付可验证；不以模拟成功代替真实执行。

具体支持的文件格式、模型接入、持久化方式及首批能力包，在技术核验后列入实施方案。跨会话调用、完整 Fork 交互和能力雷达不因在讨论中提到就自动成为首版必做项。

这里的跨会话调用指 Agent 自动访问或执行其他会话，不含用户确认后的固定内容接续；后者属于本次首版建议范围。

## 7. 前提与产品方案取舍

沿用已经讨论并接受的前提：用户需要的是理解营销背景、围绕成果推进工作的专业 Agent；不是强制营销流水线；现成开源能力值得复用；研究可独立结束也能继续策略。没有再做一遍定位访谈的必要。

历史产品取舍：报告式工作稿作为唯一中心已不采用，因为不能充分表达方向组合与局部操作；纯聊天无法承担成果修改和交付；选择可操作营销成果为中心，报告作为同版本视图。这里记录已有选择，不重新发起竞争性方案投票。第 5 节三条代码复用路线尚未选择，不冒充已经走完技术选型。

## 8. 整合后的交互约定（本次审议范围）

| 用户操作 | 设计要求 |
|---|---|
| 开始工作 | 直接输入目标；可加资料、选已有背景，或按需建立品牌背景。角色、官网等辅助理解，不是必填向导 |
| 查看工作区 | 左侧为可切换会话，中间对话，右侧成果；计划和依据按需展开。浅暖灰、白色工作面、少量紫色强调沿用当前图稿，不把每个状态做成独立路由 |
| 使用方法 | 通过目标和上下文推荐适合的方法，说明用途及必要输入；用户可调整。不要求用户理解 Skill 技术术语或先选方法才能工作 |
| Ask／Plan／执行 | Ask 解释不改成果；Plan 讨论和保存范围不制作；明确开始才执行。模式不强制顺序，执行也不自动采用、发布 |
| 保存和开始计划 | 保留交付项身份与顺序；一个明确待执行项可直接开始，多项且范围含糊时选择当前项或全部；未保存调整须明确选择处理方式 |
| 形成方向 | 按任务需要给一个或多个选项，展示受众、表达、资源、KPI 假设与依据差异；组合 A/B 时形成新成果或候选，不覆盖原方向 |
| 手动编辑 | 普通编辑直接保存为工作修订，不增加审批动作；已引用或已采用的历史内容不能原地重写。保存粒度可在工程方案确定，但每个可引用版本必须可恢复 |
| Agent 局部修改 | 绑定成果、基础版本和段落，形成候选；只改选定范围。基础稿后来变化则提示比较，不静默覆盖；采用由用户决定，查看和采用分开 |
| 阅读与交付 | 工作视图和报告视图使用同一指定版本；报告自动组织结论、推导、依据、假设和局限，配合有意义的表格／图示，不让用户重新整理聊天 |
| 选择性接续 | 预览所选片段、版本和必要背景，确认后创建工作但不自动发送；新工作可排除引用，原资料不整包复制 |
| 来源与版本 | 使用固定摘录及来源定位；新来源不改旧快照。版本不存在或片段缺失时说明，不静默换成整份或最新版 |
| 切换与异常 | 恢复工作草稿、计划和查看位置；后台完成只更新所属会话。取消后返回的结果不得自动写入成果或标记任务成功；中断后明确待重试，不伪造成功 |

上述是正式实现应遵守的行为，不是对当前图稿实现完整性的陈述。尤其当前图稿允许来源编辑后提示旧引用；正式版要求历史引用身份不可变，不能直接照搬图稿的内存数据实现。

## 9. 分发、依赖与尚未决定的事项

分发渠道、安装方式和 CI/CD 明确暂缓决定，待底座核验后随工程方案确定；“开源”不等于已经有可下载安装的发布包。首次可用版本必须交付可复现的启动方式、依赖说明与真实能力边界，不能只有演示 HTML。

技术依赖：宿主许可证及扩展点、模型执行、资料读取、搜索来源、版本存储与恢复、文件输出。目前均不因原型有对应按钮就视为落实。
