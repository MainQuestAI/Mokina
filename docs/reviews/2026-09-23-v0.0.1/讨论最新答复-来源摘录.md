## 一、这次重新核对，得到哪些直接影响开发范围的结论

本轮重新查询了默认分支，并将源码核对固定在：

**`nexu-io/open-design@ac6115406f3f780ef5c624a9aad1a87cbbad882a`**

这是本轮默认分支查询返回的提交，不沿用之前调研的旧提交。

本轮读取了实际路由、首页与项目组件、文件工作区、编辑接口、版本模块、导出接口、运行适配、提示组合、营销任务配置、研究技能、研究实现和资料预览实现。**属于固定源码静态核对，没有启动桌面、调用模型或执行测试；实际接入与运行结果需要 Codex 核验。**

### 1. 项目与文件工作区已经存在，不需要再造“营销项目系统”

当前路由已经能直接定位项目、项目内会话和项目文件；应用架构也已经区分 Web、daemon 和 Electron 的职责。Mokina 应当调整的是**用户进入项目后先看到什么、怎样找到和继续处理成果**，而不是新增另一套 Project、Task、Artifact 管理系统。 

**开发含义：保留实体与底层机制，修改入口、默认打开行为和呈现优先级。**

### 2. 终端入口已经被弱化，不需要重复做一轮“去 Coding 化”

工作区的标签启动器中，`ENABLE_TERMINAL_WORKSPACE_ENTRYPOINT` 和 `ENABLE_BLANK_PAGE_WORKSPACE_ENTRYPOINT` 当前都是 `false`。也就是说，“新建终端”和“新建空白页面”已经不是默认开放入口。

**开发含义：保持即可，不再安排“删除终端界面”的重复工作，更不能因此误删 Agent 读取、修改文件的执行能力。**

真正需要继续弱化的，是营销工作中的技术配置负担，而不是源码里是否出现 Terminal、CLI 或 Tool。

### 3. 现有 `marketing` 配置不能直接等同于 Mokina 的营销专业能力

上游的营销任务 profile 重点包括渠道、画布尺寸、传播信息、CTA、品牌素材、多尺寸变体，以及海报和渠道视觉的 HTML 源文件交付。这是有价值的营销视觉生产能力，但不是已经覆盖市场分析、目标拆解和营销方案推导。

**开发含义：保留原有视觉营销能力，另外增加“市场／营销分析”和“可操作营销方案”，不能只把首页改名后继续调用原来的视觉任务配置。**

### 4. 改一个 Skill，不保证所有入口都会使用它

当前提示组合存在 legacy 与 OD Next 两条路径；源码中，是否属于自动默认场景、任务类型及运行条件，会影响实际走哪条路径。 

**开发含义：V0.0.1 必须确定并实测一条稳定的营销运行路径。**

需要检查首页开始、项目内继续、局部修改、选择性接续是否都加载正确的方法和 reference。否则很容易出现：第一轮像营销顾问，第二轮又变回要求确认画布尺寸的视觉设计助手。

但这不意味着要先治理整个上游提示体系。**只改实际使用的路径，不先重构所有运行通道。**

### 5. 版本与导出已有基础，主要是补语义，不是重建系统

文件版本模块已有版本 ID、内容摘要、父版本及锁；HTML 导出接口也已经接受 `versionId`。因此，不能再把“建设版本系统”“建设指定版本导出”整体作为新开发项目。 

需要特别处理的是：聊天成果卡的点击语义仍然指向工作区当前文件，不能直接承担“查看当时版本”“引用这版结论”。

**开发含义：复用现有版本库与导出链，连通候选、采用、历史查看和固定引用。**

### 6. 资料读取和研究也不是从零开始，但必须检查“实际进入工作”

文档预览代码已经包含 PDF、DOCX、PPTX、XLSX 的处理路径，其中 PDF 文本提取依赖 `pdftotext`；研究实现已经包含真实 Tavily 调用，以及缺少配置、没有来源时的错误处理。它们不能自动证明上传内容已经进入模型上下文，或研究结果已经达到营销分析要求。 

**开发含义：先复用读取和检索能力，重点验证资料是否真正影响结果，不再另建文档平台和搜索平台。相关依赖、授权与实测需要 Codex 核验。**

## 二、哪些该留：主体能力保留，不先做代码瘦身

以下“保留”是产品与开发取舍，不代表已在 Mokina 中集成通过。

| 功能板块 | V0.0.1 建议 | 具体边界 |
|---|---|---|
| **Web、Electron、daemon 与共享协议** | 完整保留 | 不换框架，不增加第二套前后端，不重写运行服务 |
| **项目、最近项目、项目文件入口** | 保留并调整优先级 | 用户可以从项目直接找成果，而不是先翻聊天 |
| **文件上传、目录、多标签与预览** | 保留 | 在原工作区区分资料和交付物，不建设新的文件中心 |
| **HTML 成果预览与展开阅读** | 保留 | 作为分析、方案和其他成果的统一工作面 |
| **直接编辑、保存、撤销和重做** | 保留 | 默认突出内容操作；技术属性放入高级编辑 |
| **版本历史、快照和恢复** | 保留 | 在原机制上补候选、采用、引用关系 |
| **对话、执行进度、取消、恢复与后台工作** | 保留 | 会话退到协作层，但不能删除并行与可靠运行能力 |
| **模型检测、现有授权与 BYOK** | 保留 | 首轮集中验收一个主通道，不删除其他已有适配 |
| **Skills、插件、模板与 reference** | 保留 | 作为营销能力的主要扩展位置，不新造技能平台 |
| **Design System 与品牌视觉资产** | 保留 | 营销成果同样需要品牌一致性，不因“不是设计工具”而删除 |
| **原型、演示文稿、图片、视频等制作能力** | 保留，移入更多能力 | 不作为本轮新增研发重点，但保留用户主动使用的可能 |
| **导出、设置、错误提示和本地日志** | 保留 | 按已验证格式和实际就绪状态开放，不用隐藏错误换取“流畅” |

这份保留方案对应的现有基础，可以在应用分层说明、项目组件、文件工作区、编辑面板和导出代码中找到；这些模块能否直接满足 Mokina 的具体行为，仍然**需要 Codex 核验**。   

**尤其不建议删除品牌视觉、图片和演示文稿能力。**Mokina 的首版重点不在这些地方，不等于营销人员不会用到它们。删掉后再补回来，反而违背完整复用的初衷。

## 三、哪些该删：重点删除上游专属产品绑定，而不是通用能力

### 1. 建议从 Mokina 本地首版中去掉的内容

当前入口代码中，可以看到上游账户、余额、升级、团队、活动及更新相关组件和接入。下面是针对这些路径的**删除／停用建议**，不是说应该直接清空所有相关源码。 

| 对象 | 建议处理 | 必须保留的边界 |
|---|---|---|
| **上游云账户的充值、余额、升级和促销入口** | 从 Mokina 本地版移除入口及主动触发 | 保留模型供应商的真实授权与 API Key 配置 |
| **上游专属团队、席位、成员及商业控制台入口** | 本地个人版关闭，不新增自己的企业账号系统 | 不连带重写项目身份、数据隔离和共享协议 |
| **促销活动、增长调查、推广归因和星数拉取** | 取消挂载和触发；独立组件可移除 | 保留本地故障诊断和用户主动反馈 |
| **向上游发送的产品遥测** | Mokina 首版默认不发送，并检查实际请求 | 不能只是隐藏开关，后台仍继续发送 |
| **上游自动升级通道** | 停用，避免把 Mokina 更新回上游产品 | 不因此要求本轮开发自己的更新服务 |
| **上游支持邮箱、商业跳转和产品身份文案** | 换成 Mokina 的已确认入口；没有地址就不显示 | 保留应有许可证、版权和归属声明 |
| **旧独立 `/mokina` 工作台的继续扩建** | 停止；核验后解除活跃入口，保留历史参考和测试资产 | 不根据讨论中的路径直接删除本地文件 |

**没有必要把“去掉上游登录”实现成“放开所有鉴权”。**正确方向是使用本地个人工作路径和自己的模型授权，而不是伪造云端登录状态。

根许可证要求保留相应许可、修改声明和归属信息；更换产品名称不意味着去掉这些内容。第三方插件、素材及依赖的具体许可，仍然**需要 Codex 核验**。

### 2. 这些只是收起，不建议物理删除

**多模型目录、全量插件市场、Figma／代码迁移、网站复刻、WebGL、复杂设计检查器、自动化、桌面宠物，以及图片／视频／音频专用入口**，可以退出营销默认路径，放入设置、更多能力或高级操作。

其中两种情况要分开：

**用户低频使用的能力，收起入口。上游专属商业绑定，关闭实际触发。**

不能都靠一个“隐藏菜单”解决，也不需要为收起一个菜单先进行全仓库依赖清理。

## 四、V0.0.1 必须改的十项功能

下面这十项是我建议直接进入开发的清单。**不是十套新系统，大部分应当是对既有机制的连通和小幅调整。**详细上游定位和验收条件已经写入附件。

| 编号 | 功能 | 用户应得到什么 | 最小实现方式 |
|---|---|---|---|
| **F01** | 产品身份与本地运行隔离 | 启动的是 Mokina，数据不混入原 OpenDesign，不要求购买上游云服务 | 修改外显身份，独立数据根，停用上游商业／遥测／更新触发；保留内部包名与协议 |
| **F02** | 营销首页与默认导航 | 直接提出营销问题、添加资料、开始工作 | 复用原首页；增加“市场与竞品分析”“营销方案”快捷入口，保留自由开始和更多能力 |
| **F03** | 项目内交付物优先 | 回到项目就能继续处理成果 | 恢复上次打开的交付物，突出成果与资料，允许收起讨论；不新增项目管理流程 |
| **F04** | 资料进入工作与依据留存 | 上传内容真正影响判断，能回看当时依据 | 复用上传、解析、研究和上下文机制；补实际使用记录、固定摘录与来源定位 |
| **F05** | 两个营销场景包及公共 reference | 生成专业分析和可操作方案，不是换标题的通用报告 | 两个场景包，共用必要 HTML 结构、来源表达和质量检查；不先建设几十种理论模板 |
| **F06** | 稳定的营销运行绑定 | 开始、继续和修改都使用正确的方法 | 固定首轮主运行通道与营销提示路径，检查真实加载内容；不全仓重构提示系统 |
| **F07** | 直接编辑与 Agent 局部候选 | 自己改字直接保存；AI 修改可以比较、采用或放弃 | 沿用选区和编辑机制，先保证章节级修订；候选绑定基础版本，不覆盖用户后来的修改 |
| **F08** | 历史、采用与指定版本导出 | 看的是哪版，交付的就是哪版 | 复用版本库和 `versionId` 导出；明确当前稿、历史版、候选，固定必要资源 |
| **F09** | 选择性接续 | 选定结论，带到下一项工作 | 预览片段、版本和必要背景；确认后准备新请求，不自动发送、不复制整段聊天和目录 |
| **F10** | 运行、切换、恢复和失败状态 | 能并行工作、关闭重开，失败不冒充成功 | 复用真实流式与恢复机制，定向修补；后台结果不抢屏，取消后不自动采用迟到结果 |

这十项中的本地文件落点、可直接复用比例、当前实现状态及通过结果，全部**需要 Codex 核验**。

### 三处需要特别控制实现重量

#### 第一，项目优先，不等于新增项目总览大屏

直接沿用原项目入口和文件工作区即可。

用户重新打开项目时，优先恢复当前交付物；没有打开记录时，展示已有成果和资料。**不需要为了“项目中心”再开发进度看板、负责人、里程碑管理和项目 KPI 大屏。**

同一个项目可以有多个成果，但不应新增一套与上游文件竞争的“营销资产库”。

#### 第二，HTML 统一，不等于每份报告都是一个新应用

建议先提供两个成果结构：

**市场／营销分析：**问题范围、关键判断、比较矩阵、证据、推断与局限。

**营销方案：**目标／KPI、受众、方向、行动与渠道、预算和周期约束、验证建议。

已有 `research-decision-room` Skill 提供了证据台账、主题、决策备忘录及 HTML 组织方式，值得调整复用；但它原本面向产品与设计研究，不能不加判断地套用到所有营销任务。

首版不必建设通用 schema 驱动编辑平台。**让两个真实成果可读、可改、可引用，比先做十几种“理论模板卡片”更重要。**

#### 第三，局部修改先做到章节级，不追求万能编辑器

用户可以直接编辑正文；让 Agent 修改时，绑定一份成果、一个基础版本和一个章节，形成候选。

这既保留了已经确认的“Agent 修改由用户采用”，也不把普通手工编辑变成审批流程。:chatgpt-content-reference{index="21"}

实现上应优先复用现有定位和 patch 能力。**不能只在提示词里写“不要改其他内容”，然后把整份新 HTML 覆盖回去。**

## 五、这一版的用户路径应该是什么样

不再另外设计一套五六个页面的向导，直接在原产品中贯通下面的工作。

### 开始

用户打开 Mokina，看到目标输入、最近项目和两个营销快捷入口。

输入：

> 基于这些品牌、产品和目标资料，帮我形成新品上市营销方案。先讨论方向，不要立即制作完整方案。

可以上传资料；没有 Brand Kit 也能开始。项目在工作开始时形成，不要求先填完整项目表单。

### 讨论与形成成果

Agent 读取实际资料，只追问确实影响判断的缺项。用户要求讨论，就停留在讨论；明确要求形成方案，再生成 HTML。

成果出现在原工作区，成为主要阅读和操作对象。对话仍然可展开，但不是寻找成果的唯一入口。

### 修改

用户直接修改一句正文，保存。

再选中“渠道安排”章节：

> 保留总预算和周期，把渠道重点改为线下体验与内容种草。

Agent 形成局部候选，用户比较、采用或者放弃。未采用之前，当前稿不被替换。

### 接续与交付

用户选中两条结论，点击“以此继续”，看到要带入的片段、版本和必要背景，再开始另一项工作。

这里需要检查真实运行输入：现有上下文辅助代码会把项目／本地代码引用解析成关联目录，因此，**选择性接续不能只是界面显示两条结论，后台仍开放整个原项目目录。**

最后，用户导出指定版本，关闭产品，再次打开仍然能找到项目、成果和历史。

**这条工作跑通，才是 V0.0.1；不是首页换成 Mokina、模型能回复几句话就算完成。**

## 六、怎样快速搭建：三个连续交付点，不再先做一轮泛研究

### 交付点 A：真实底座在 Mokina 身份下运行

先固定上游提交和锁文件，记录原始启动基线，使用独立数据根和已授权的主模型通道，调整必要身份与上游专属接入，然后真实生成并保存一份成果。

**建议首轮集中验收 Codex 通道，保留其他已有适配，不同步扩展多个运行底座。**上游已经有 Codex 的检测、授权探测、模型列表及运行定义；本机版本、授权和实际执行需要 Codex 核验。 

不要在这个交付点之前换技术栈、重写组件库、统一全部包名或清理所有非营销功能。

上游当前文档的开发入口是 `pnpm tools-dev run web` 和 `pnpm tools-dev`，环境基线为 Node 24、pnpm 10.33.2。这里应沿用其启动工具，不另造启动体系；命令在 Mokina 本地是否通过，**需要 Codex 核验**。 

### 交付点 B：营销主线可以真实完成

接入两个营销场景包、公共 HTML reference、资料与来源处理，并调整项目和成果的显露方式。

跑通：

**资料／问题 → 讨论 → 分析或方案 → 保存 → 重新打开。**

这一阶段就应该出现真正可用的营销工作，不能仍然是全部依赖 Mock 的界面。

同时换一组产品事实和目标复跑，检查结果是否实质变化。否则只能证明模板能展示，不能证明 Agent 理解了任务。

### 交付点 C：完成 V0.0.1 的修改和交付闭环

连通局部候选、采用、历史版导出、固定接续、后台工作和重启恢复。

验收不必膨胀成完整 benchmark，先完成八项：

| 验收项 | 必须观察到的结果 |
|---|---|
| **真实启动与连接** | 不依赖上游商业账户；已授权模型真实执行 |
| **两类成果** | 分析与方案有不同结构，输入实际影响判断 |
| **资料与来源** | 能检查使用了什么，排除生效，真实取源 |
| **局部修改** | 范围外不变；候选、采用和冲突行为正确 |
| **版本与导出** | 导出的确实是所选版本，在应用外可打开 |
| **固定接续** | 只带所选内容和必要背景，不自动发送 |
| **并行与异常** | 后台不抢屏，取消和失败不伪造完成 |
| **关闭与重启** | 项目、成果、历史与引用仍然存在 |

**这些是建议的完成标准，不是已通过的测试结果；需要 Codex 核验并留下真实证据。**

## 七、我建议这轮明确不做的事情

**不做另一套高保真静态原型；不扩建旧独立工作台；不做多底座统一平台；不做企业权限与审批；不做自动投放发布；不做完整视频制作适配；不做自动 Skill 安装雷达和长期自演化系统；不先发布全平台安装包和自动更新服务。**

但上述“不做新增适配”不等于删除 OpenDesign 已经提供的对应能力。现成能力保持可选，首轮只对明确范围给出验收承诺。

最后交付应当包含：**可复现源码、固定上游版本、依赖与启动说明、真实模型通道、两个营销场景包、真实生成样例、验收记录和明确的能力边界。**这也符合现有收口稿对“首次可用版本不能只有演示 HTML”的要求。:chatgpt-content-reference{index="27"}

**我的建议是按这份清单进入搭建：用 OpenDesign 已有的完整产品能力压缩开发量，把这一轮真正新增的工作集中在营销场景、成果使用方式，以及几处不能含糊的编辑和引用行为上。V0.0.1 的终点是能够拿自己的资料完成一项营销工作，然后明天还能接着用。**
