## 2. 必须延续的产品决定

### 2.1 定位

Mokina 是面向营销专业人士、以项目和成果交付物为中心的开源 Agent 工作区。它首先保留通用 Agent 的开放工作方式，再通过营销方法、行业视角、品牌背景、Skill 和 reference 模板形成专业适配。[S6]

用户可以直接提出问题或目标，也可以带着资料、品牌和 KPI 开始。项目负责组织工作，但不要求用户先填完整项目表单、建好 Brand Kit 或选完专业方法。会话负责讨论与执行，不应成为寻找成果的唯一入口。

### 2.2 成果与能力

HTML 是产品内统一的成果呈现与操作载体，不是把所有输入强制改成 HTML。原始 PDF、表格、图片等保留原格式；成果可以包含图表、矩阵、图像、视频及对应数据和来源。对外导出绑定明确版本。[S6]

Skill 提供方法、判断步骤、输入要求和质量要求，reference 提供相应 HTML 结构及示例。不能把专业能力做成只有标题的模板，也不能把所有方法强制塞进每个任务。

研究、策略、品牌/视觉、内容和效果分析是可组合能力，不是必须依次走完的状态机。接续工作是用户选择，不等于自动启动下游任务。

### 2.3 复用与减法

继续在完整 OpenDesign 原生宿主内迭代，不扩建独立 `/mokina` 前端，不合并两套会话、运行或存储机制。未讨论的能力默认保留。[S6]

品牌规范、素材、设计、内容生产和导出，不因为带有“设计工具”特征就整块删除。优先调整营销用户的默认入口、术语和常用操作；非核心高级入口可以收起，底层能力保留。上游专属商业接入按已确认的本地版边界处理，不能一刀切关闭用户主动使用的外部能力。

## 3. 路线与版本划分

版本划分是建议，工程继续使用原生 `V0.0.x` 序列；历史讨论稿中的 v0.3、旧 V6.2 原型编号不直接等同原生发布版本。

| 里程碑 | 用户可感知结果 | 主要内容 | 不承诺的扩展 |
|---|---|---|---|
| V0.0.2 收口 | 从首页开始，使用自己的资料，形成、修订、接续和交付一个真实营销成果 | 原生导航与资料体验、最小品牌/素材约束、接续生成、设计迁移核对、桌面回归 | 企业项目管理、全渠道发布、完整能力市场 |
| V0.0.3 | 不只完成一次任务，而是可重复利用品牌背景和专业方法 | 背景复用、现有两个营销场景深化、第三类开放任务验证、小规模能力选择 | 大型知识中心、全行业模板库、自动技能安装 |
| 后续探索 | 逐渐理解用户的工作方式并推荐合适能力 | Meta Skill 的可确认偏好与能力组合建议 | 静默改写 Skill、自动改变品牌规范、自主安装或执行外部动作 |

V0.0.2 不应只剩“八页像素迁移”。先回放真实链路，再逐批完成体验，最后核对设计与桌面发布。视觉一致性与业务可用性同时推进，但不以高成本材质特效替代真实工作验证。

5. 核验冻结设计包内容，建立唯一的视图迁移清单：设计视图、现有入口、当前实现、缺口、所属批次、验收证据。清单服务实施，不再另做完整方案研究。

**验收：**最新构建与源码身份明确，最小真实任务能完成或定位出具体失败点；既有原型与原生产品入口清楚区分。本地状态、命令与测试结果**需要 Codex 核验**。

**边界：**不要求先清零上游全部历史失败；新增回归必须修复，既有无关失败需有可核对基线，不得直接忽略。

### B1：首页、全局导航与项目/成果入口

**业务问题：**用户不应先理解 Coding Agent 的会话、文件夹或设计类型，才能开始营销工作；也不应翻聊天找成果。

**开发范围：**

- 首页提供“直接提出问题/任务”的主要输入方式；分析、方案、内容等仅作可选示例，不形成强制流程向导。
- 最近项目呈现项目名称、最近成果、当前运行或待处理状态；从成果直接回到工作区，从项目继续相关工作。
- 沿用宿主导航和标签状态，处理首页、项目、成果、后台工作之间的往返；保留草稿、文件与当前工作身份。
- 明确资料入口和已有背景的可选入口，不要求首次使用先完成背景建档。
- 在本批涉及的页面和设置中统一 Mokina 品牌与营销术语；非核心开发型功能归入“更多/高级”，不删除品牌与制作能力。
- 接续创建后的项目名称与成果入口继续沿用 PR #2 修复，不回退成纯会话列表。

**不做：**新建 Work 数据模型、重写路由/标签系统、企业项目看板、负责人/审批/排期管理、复制设计原型的 localStorage。

**验收场景：**从空首页直接开始；从最近项目打开指定成果；A 运行时切到 B，A 完成不抢占 B；B 的草稿刷新后可恢复。所有可见交互在完整宿主中用普通点击与键盘验证。

**交付：**一个可独立合并的导航切片；后续批次未接入的能力不得用假成功按钮占位。

### B2：资料、背景与本次运行依据

**业务问题：**用户需要知道 Agent 实际拿到了什么，不是只知道文件已经上传。

优先复用 V0.0.1 的资料解析、位置标记、选择与固定摘录路径；现有代码能否直接承接以下行为**需要 Codex 核验**，不能预设要另建解析/RAG系统。

**前端与上下文要求：**

| 信息 | 用户需要看到什么 | 证据来自哪里 |
|---|---|---|
| 文件已保存 | 文件名、格式、所属项目，能够打开原件 | 原生文件记录 |
| 提取结果 | 可读、部分可读、失败、超限或不支持及具体原因 | 资料读取接口的实际响应 |
| 本次选择 | 用户明确选择的资料、背景、品牌规范和素材 | 当前请求的选择状态 |
| 已传入运行 | 本次实际发送的输入范围及快照身份 | 实际运行输入/上下文组装记录 |
| 成果依据 | 结论引用的摘录、位置、来源版本 | 成果引用与真实读取证据；不能由“已上传”推定 |

这些是语义要求，不要求界面常驻五张状态卡。默认给出简洁摘要，细节按需展开。

**开发范围：**

- 文件导入、提取结果预览、逐份选择/排除、实际请求中的资料确认。
- 复用已有 PDF/Word/表格等解析能力；对现有支持范围进行回归，而非承诺所有复杂格式都支持。
- 表格缺公式缓存、扫描件不可读、超限和读取失败等，保留限制信息；不能把部分内容显示成“已完整理解”。
- 区分项目背景、品牌规则、当前要求和个人偏好。当前任务的例外不能自动变成永久品牌规范。
- 品牌与视觉规范在本批完成最小接入：用户可选一份已有规范和必要产品事实，影响本次生成；跨项目大型背景管理后置。
- 原件变化后明确提示当前请求使用的是哪个快照；历史成果的来源不被静默更新。

**数据边界：**优先复用现有项目元数据、文件、运行记录和固定摘录，不新增一个独立“知识中心”。资料选择意味着本次上下文的选择，不等同于对通用 CLI 所有文件访问权限的强制隔离。

**验收：**选定资料中的业务条件进入运行；未选资料不因默认整包传入而污染结果；能回看结果依据；资料变更不改写旧引用；部分读取反馈与实际结果一致。允许在不影响任务的缺口下继续，不做“一项缺失全局禁用”。

### B3：真实接续制作与成果精修

**业务问题：**已有分析和方案不能只停留在报告，应能成为下一项成果的明确输入。

本批主样例建议为：**营销方案中选定一段策略＋品牌规范＋指定素材→独立活动页任务→真实生成 HTML→局部修订→指定版本导出**。这是验收链，不是强制产品流程。

**开发范围：**

- 沿用当前固定摘录与独立接续项目机制；复用 `MOKINA-CONTINUATION.json` 的现有承载，字段与接口调整**需要 Codex 核验**。
- 接续前展示所选来源版本、章节、补充背景、选用品牌与素材，用户可以删减或修改请求。
- 创建后保留未发送草稿；明确发送后才运行，不把点击“继续制作”解释为自动执行。
- 活动页优先使用已有宿主制作能力与 reference，不另建页面生成引擎。
- 成果能回看所用来源；上游后来改变不静默修改已生成页面。
- 局部修订继续复用候选机制。优先展示所改章节、基础版本与候选差异；需要并排时复用现有预览，不新建第二套版本系统。
- 手工修改直接形成工作修订；AI 候选由用户决定是否采用，普通编辑不增加审批环节。

**专业要求：**选定的人群、卖点、渠道条件、品牌表达和 CTA 在页面中真实出现；资料不足时明确假设，不把无关模板换品牌名当成完成。选用图片应实际用于成果与导出，不能只有素材卡可见。

**验收：**真实模型输出落盘并可再次打开；指定章节修改不改变其他业务内容；未采用候选不替换当前稿；历史版本导出与选择一致；接续所选/未选内容保持边界；取消/失败后能够在原生流程中恢复或重试。

### B4：设计迁移核对、桌面回归与发布说明

**目的：**将分批可用的能力收成可供持续使用的 V0.0.2，而非把局部浏览器通过写成桌面发布通过。

**开发范围：**

- 按 B0 的八类视图映射补齐实际缺口；已有满足项直接复验，不重做。一个设计视图可能是面板或状态，不自动新建路由。
- 统一首页、项目/成果、资料、修订、接续及相关菜单的设计体系；长文阅读、短窗口可操作性和主要按钮优先于复杂玻璃折射。
- 继续落实当前冻结的中性玻璃设计；未完成的高级材质列清状态与批次，不擅自删需求，也不让其阻塞真实工作链的提前验证。

- macOS 原生宿主验证启动、模型连接、资料选择、真实生成、局部修订、重启恢复与至少一种正式可用交付路径。桌面导出与浏览器后备路径分开标注。
- 更新根 README，让原生运行指引在前，V6.2 历史原型后置；启动命令、依赖、数据目录、模型授权前提均以 Codex 实测结果为准。[S7]
- 以最小可维护方式连接核心检查到仓库 CI；是否已有适用入口**需要 Codex 核验**。不机械搬入整套上游发布/商业流水线。

**不做：**本轮同时承诺 Windows/Linux、全渠道自动发布、全部高级导出格式、企业协作、多底座一致性或完整签名自动更新体系。分发形态仍按实际能验证的结果确定。

## 5. 三个持续使用的验收任务

应使用少量稳定任务贯穿开发，不每轮重新编造一批漂亮样例。下面的业务素材为建议的合成样例，不是客户事实。

| 任务 | 主要目的 | 输入和动作 | 通过条件 |
|---|---|---|---|
| A：研究/策略工作 | 验证营销判断受输入影响 | 品牌/产品事实、预算周期、渠道约束、两份访谈或已有研究；先讨论再生成方案，随后只改一个方向 | 事实与假设区分，推荐有取舍，预算/渠道/周期相符，未选章节保持，来源可回看 |
| B：策略接续活动页 | 验证研究不是孤立报告 | 从 A 的固定版本选一段，带指定品牌规范与素材，创建后确认发送 | 只带指定来源，品牌与素材实际生效，生成可阅读HTML，局部修改与导出绑定版本 |
| C：开放式数据任务 | 验证通用 Agent 能力未被两个预设场景封死 | 上传小型 CSV，计算明确指标，解释变化并选两条结论接续 | 数字来自实际计算，口径可复查，不把相关性自动说成因果，不强迫走品牌/上市流程 |

A、B 是 V0.0.2 的核心完整链路；C 是轻量通用性抽测，不为它新建分析工作台。若现有通用执行能力不够，明确最小缺口和承接批次，不能假造成功或因此扩成完整 BI 产品。

补充一组输入敏感性对照：同一任务换掉预算、目标人群或禁止渠道，检查关键建议是否随之变化。结构相同并非失败，但违反新条件或照抄旧建议不能通过专业验收。

## 6. V0.0.3：从一次可用到持续复用

### 6.1 项目背景与品牌规范复用

在 V0.0.2 最小品牌接入基础上，允许用户保存和选择常用品牌/产品背景、表达规范、视觉规范与常用素材。展示本次使用哪一版；临时修改只作用于当前任务，升级为长期规则需要明确动作。

优先利用现有 Design System、文件和项目背景机制；具体可以直接复用哪些**需要 Codex 核验**。不默认另建品牌管理数据库或 DAM。

### 6.2 深化两个现有营销场景包

现有 `mokina-market-analysis` 与 `mokina-marketing-plan` 先做质量深化，不重建一组同义 Skill。[S3]

每包至少明确：适用问题、输入、缺项处理、专业判断、证据要求、HTML reference、局部修改范围和质量检查。研究可以结束为独立成果，方案也可以直接从 Brief 开始。

后续基于真实使用频次选择一种内容生产或运营分析能力补充。新增能力以 Skill/reference 优先，不把每个方法变成一个一级页面，也不把营销方法全部硬编码进宿主。

### 6.3 可理解的能力入口

用户先看到“适合解决什么问题、需要什么资料、会交付什么”，技术 Skill 信息放到详情。复用已有安装/启用机制，先做小规模可信能力集合；不同时开发插件市场、排序推荐系统与自动安装雷达。

## 7. Meta Skill：保留方向，分两步落地

Meta Skill 不应被缩减成“记住语气”。它的目标是根据历史沟通、交互与反馈，理解用户实际工作方式，发现更合适的能力，帮助组合与配置，持续调整个人工作方式。

**近期仅保留低成本基础：**区分任务事实、品牌规则、个人偏好；允许用户显式保存常用表达/交付结构；保留必要的采用、修订、拒绝理由。不要为未来学习提前建设大型行为采集系统。

**后续形成最小闭环：**识别重复偏好或能力缺口→给出具体建议与依据→用户确认→限定范围应用→可以修改或撤回。能力安装与外部执行沿用明确授权，不从“推荐”自动变成“已执行”。

例如：多次将方案改为“结论/依据/行动”，可建议保存个人交付偏好；频繁做渠道数据复盘，可建议启用适合的分析方法组合。不能因为一个品牌的一次任务如此，就修改所有品牌或永久重写 Skill。

## 8. 研发组织与依赖

建议顺序：`B0 → B1 → B2 → B3 → B4`。每个功能批次原则上一个可独立合并的 PR；B0 是基线工作，只有产生实际修复或说明变更时才需要 PR。不预占 GitHub PR 编号。

可并行的工作：B1 导航实现期间，准备 B2 的接口复用清单与 A/B/C 验收资料；B2 期间深化现有 Skill/reference；B3 期间准备桌面与发布验证。是否切分并行分支依据具体共享文件判断。

不建议多个 Agent 同时修改 `App.tsx`、`ProjectView.tsx`、`FileViewer.tsx` 等共享入口。由一个主执行 Agent 负责集成；其他 Agent 负责独立任务、测试、只读审查或能力包。当前代码耦合与任务边界**需要 Codex 核验**。

每批只保留四类必要记录：目标/非目标、改动与复用位置、可执行验收、当前提交与真实结果。不要求每轮重写全套 PRD/SOW，不建立健康分作为放行依据。

排期采用验收批次，不给无依据的日期或人力投入承诺。完成 B0 后按已核实缺口、依赖与验收结果调整批次顺序。真实模型链路在 B0 提前验证，不能等 B4 才首次启动。

## 9. 本轮明确不做

- 换底座、建立多 harness 插拔平台，或重新开发独立工作台。
- 把研究、策略、品牌、内容、发布、复盘设成必须走完的流程。
- 企业项目管理、审批/责任移交、客户级权限治理等 Lilith 式业务系统范围。
- 大型知识中心、品牌 DAM、全渠道分发、完整视频生产线、全行业方法库。
- 自动安装/自动进化 Skill、静默写入长期品牌规则、自动对外发布。
- 为保持“原样复用”而忽略真实交互缺陷，或反过来以品牌适配为名删除所有设计能力。

未来能力可保留扩展位置，但不为尚无真实任务支撑的扩展提前增加持久化对象、平台层和长链路校验。
