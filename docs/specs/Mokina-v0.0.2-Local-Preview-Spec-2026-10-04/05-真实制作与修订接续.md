# 05｜真实制作、修订与接续（B3）

## 5.1 原有场景先变得真正可用

保留 `mokina-market-analysis`、`mokina-marketing-plan` 两个手动入口。生成主链必须通过原生场景/Skill 组合，使已有 `report-contract.md` 的自包含 HTML、稳定章节 ID、来源、数字口径与打印要求实际进入模型上下文。修改提示词必须同时核对仓库 `docs/prompt-composition.md` 中的两条实现路径，不能只改一个 prompt 文件就称已接通。[S03/S09]

新增 `mokina-landing-page` 仅是一个薄场景：复用现有品牌/设计/HTML 制作、资料读取和导出工具，声明活动页输出契约；不另造 Agent Loop，不引入固定任务流引擎。用户仍可讨论、暂停、修改要求或执行其他营销任务。

## 5.2 专业结果最小标准

市场分析需区分已提供事实、推断和缺口；有明确分析对象、比较口径、优先机会和限制，不用空泛大词替代结论。营销方案需给目标、目标人群、主要判断、渠道取舍、行动、预算和评估方法，预算合计与约束一致。没有外部证据不得编造市场规模、竞品价格或行业增长率。

活动页需呈现选定策略对应的人群、核心价值、产品事实、行动入口和合理结构；品牌规则、禁止表达和所选素材确实影响产物。没有表单后端时 CTA 只能跳转到用户给定合法目标或明确标记预览交互；不能虚构成功提交、真实转化或已发布。

没有视觉素材时可以制作文字/排版为主的真实页面，并提示需要补图；不强制购买图片生成服务。若用户选了素材，则不得用无关占位图冒充已使用。通用内容制作能力继续通过原生能力提供，但本版不把社媒发布等外部副作用纳入自动执行。

## 5.3 单章修订：先修发送身份缺口

现有 `generateChapterCandidate()` 已能在独立项目输出替换元素，但在收到 runId 前没有保存完整发送身份。[S10]

改成以下顺序：

1. 在源项目中确认当前版本、sectionId 和请求；记录 sourceProject/entry/baseVersionId/baseDigest。只允许当前版本修订；历史版本可先走原生恢复，产生新的当前版本。
2. 创建稳定 `operationId`、revisionProjectId、conversation 身份及 userMessageId/assistantMessageId/clientRequestId；在获得 conversationId 前，journal 可以处于 prepared 状态，但不得伪造 runId。
3. 按确定的 revisionProjectId 创建/核对独立项目，保存原章节和必要的本轮约束。写入失败时不 POST run。这个 helper 项目创建与接续共用窄恢复函数。
4. 保存完整、不可变的请求快照和 scope，await 持久写入成功后调用 PR3 受理逻辑。原 run 受理不确定时，只读核对原 clientRequestId；GET 空、超时、通用 5xx 均不能证明未受理。
5. 收到原 run 后，在既有候选路径完成结果读取和 `POST candidates`。候选写入失败可重用 operationId 保存原结果，不能因此重新运行模型。
6. 当前稿保持不变，用户看到候选再决定采用。原 run 失败/取消后，由用户明确发起新尝试，使用新 requestId，但保留与原逻辑操作的关联以防旧响应重入。

不要复制 ChatPane 的全部业务逻辑。提取/复用 PR3 的发送快照、受理回调与查询入口，形成普通发送和修订共同调用的小型 helper。scope 必须区分 **操作所属源项目** 与 **真正执行的修订项目/会话**，不能用源 projectId 去恢复 helper run。

旧 `MokinaRevisionJob` 含已知 runId 的记录仍能读取与恢复；升级为新 journal 时保留原 run/operation/baseVersion，不要求重新运行。localStorage 读取失败不等于没有历史任务。

## 5.4 候选与比较

输出必须是一个替换顶层元素，id 与 data-mokina-id 等于所选 sectionId；不接受全篇 HTML、多个顶层元素、嵌套可编辑章节或悄悄改动其他章节。继续使用已有 `replaceHtmlSection` 和 candidates API。[S07/S10]

比较展示基础版本、原章节、候选、用户要求、文本差异和来源/数值变化提示。非所选区域用字节摘要对比，不使用“看起来一样”作替代。视觉差异可预览，不能用纯文本 diff 宣称布局已经无变化。

采用只调用既有 `adopt`，必须携带 `expectedCurrentVersionId` 与 operationId。冲突时不自动 rebase、不覆盖当前稿；可重新比较/重新生成。成功后 current 指针和项目摘要按原通知机制刷新，候选和历史身份一致。

## 5.5 选择性接续

创建接续时明确选定：来源 project/entry/version、一个或多个章节、目标任务（讨论/活动页/其他明确任务）、补充背景、可选品牌规则、可选素材。默认不继承全部对话、项目目录、品牌库或未选正文。

`MOKINA-CONTINUATION.json` 从 schemaVersion 1 加法升级至 2，增加 operationId、sourceDigest、目标类型与上下文快照引用。旧 v1 按原摘录可读；没有摘要的历史记录不得伪装成经过完整来源校验。

### 创建过程的可靠性

`prepared → project-created → snapshot-saved → draft-ready` 是窄 journal 的检查点，不是新业务审批状态。

先保存确定的 targetProjectId/operationId 和选择；复用现有 createProject 的显式 ID 能力。响应丢失时用目标 ID 读取并校验 owner operation；若已有不同归属项目则冲突，不能覆盖。项目存在但资料没写好时，只补未完成的部分。写入使用临时文件+原子提交与摘要验证，所有附件完成后才显示 draft-ready。

本次 createProject 不使用首页自动发送标记；优先复用原生明确的草稿入口，没有该标记时直接保存 Composer draft/extras，**不要写 Home auto-send keys**。固定来源准备完成后才导航进入新草稿。打开、创建、恢复接续均不得调用 `/api/runs`。

切换项目或用户已经输入新草稿后，迟到的创建/读取结果不得覆盖当前输入；可显示“接续已准备好，打开该项目”。用户再次点击恢复，回到同一个 targetProjectId，不再造一个同名项目。

## 5.6 活动页接续的真实执行

用户在新草稿明确发送制作要求，沿普通 PR3 发送链运行。ctx 快照包含固定来源、品牌规则和素材字节，不跨回上游自动拉最新内容。产出保存在新项目，支持现有 FileViewer/版本/修订/导出；不往策略文件原地追加一个页面。

页面必须可寻址：稳定唯一的顶层 `id=data-mokina-id`，至少能选择真实业务章节，而不是只有一个空壳 section。具体章节由任务决定，不强迫所有活动页有同一模板。验证器只检查结构、资源和必要事实口径，不负责机械地决定营销策略正确。

## 5.7 运行成功与交付就绪分开

复用现有 deliverable/artifact 校验和状态显示，增补 Mokina 场景规则：主成果文件实际存在且非空；可读 HTML；章节可寻址；需要的资源可获取；所引用 sourceId 可匹配；数值/单位及必要约束不缺失。工程结构校验与专业人工评分分开。

原生 `current` 表示版本位置，不等于人类已批准或专业合格。首稿可以沿既有机制成为 current，但校验失败时显示“已保存，结构待修复”，不能称“可交付”。有已采用稿的单章修订继续只产候选，不因新文件写入推进旧稿。

run 已 succeeded 但没有预期文件时，保留日志与可见错误，提供用户明确触发的修复/新尝试；本版不新增自动多轮修复循环。无效文件可被检查和保存，不用强制删除掩盖失败；没有有效内容时导出禁用并说明原因。
