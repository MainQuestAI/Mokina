# Marketing Desktop Agent：v5 → v6 修改 Spec

**版本：** v0.1  
**日期：** 2026-09-13  
**用途：** 交给本地 Codex，先核查现有工程，再完成本轮修改与验收。  
**适用对象：** 用户当前本地、以 Lilith Workspace v5 为交互参考、据用户描述已接入 Codex CLI / app-server 的桌面实验项目。  
**命名说明：** “Marketing Desktop Agent”“v6”是本次产品方向和迭代标签，不要求改仓库名、产品名或发布版本号；不得自行认定这是 LilithV3 仓库。

---

## 0. 执行摘要

### 0.1 本轮究竟改什么

在保留现有桌面应用、Codex 运行链路和 v5 主要交互的前提下，将“围绕产品上市内容生产的工作台”，改成“能够承接不同营销工作的通用 Agent 工作台”。

本轮完成六项变化：

1. **工作可以独立发生。** 不创建项目，也能讨论品牌策略、制作社媒文案、分析运营数据；项目只在有组织和复用需要时关联。
2. **计划随目标生成。** 不再把 Strategy → FABE → Message House → 素材 → 渠道物料作为所有请求的必经链；已有方法仍可作为可选方案使用。
3. **让工作依据可见、可调整。** 用户能看到本次提交给 Agent 的资料、来源版本、关键缺口和排除原因；不是只展示静态“项目背景”。
4. **成果类型可扩展。** 保留 FABE、Message House、POP 等专用工作面，同时让普通文档、表格和其他文件不需要先加入一条新 workflow 才能使用。
5. **现有运行时真实驱动。** 自由输入进入本地实际接入的 Codex 链路；演示数据与真实执行明确分开，不用新增几段关键词脚本冒充通用能力。
6. **用三类任务验收。** 品牌战略、社媒内容、运营分析使用同一入口和同一协作机制；分析结果还能被用户选择性带入下一项工作。

**本轮不是重做产品，不是搭建新的 Agent 框架，不是立即覆盖所有营销专业能力，也不是开发完整 Skill 市场和自动进化系统。**

### 0.2 给 Codex 的执行方式

先完成第 3 章的只读核查，形成“本地事实 → 修改点 → 测试点”映射。若现状与本 Spec 兼容，继续实施，不必把一般实现选择逐项退回用户。只有涉及数据破坏、权限扩大、底座替换或无法兼容的重大产品冲突时，才停止受影响部分，并明确冲突与最低影响替代方案。

不得在没有源码依据的情况下照抄本 Spec 的函数名称去创建新架构；不得把“输出了核查报告”当作本轮开发完成。

## 1. 产品基线与事实边界

### 1.1 已由用户明确的方向

| 事项 | 本轮采用的基线 |
|---|---|
| 产品定位 | 面向营销人员的桌面版通用 Agent；先有通用 Agent 的灵活工作方式，再通过营销知识、技能、工具与成果交互适配专业工作。 |
| 目标用户 | 不需要熟悉 CLI、GitHub、MCP 配置和提示词工程的一般营销人员，同时允许熟练用户直接表达目标和控制执行。 |
| 营销范围 | 长期逐步覆盖战略、品牌、产品营销、内容、社媒、消费者运营和效果分析；不把现有上市内容链当作全部 Marketing。 |
| 开源策略 | 优先复用社区已有能力，项目主要承担营销工作入口、使用体验、能力组织与持续适配。开源不等于所有运行成本为零。 |
| Runtime 策略 | 本轮优先复用已接入的 Codex；多 harness 切换不是当前差异化重点。 |
| Meta Skill 方向 | 根据历史沟通和交互，发现、推荐、组合更适配用户实际工作的 skills，并根据反馈改善工作方式。该长期方向保留，本轮只留最小接点。 |
| 当前交付 | 本文为修改方案，不是已修改代码、真实运行记录或已通过测试的证明。 |

### 1.3 对前序口述建议的必要澄清

以下以本 Spec 为准，避免 Codex 机械执行过度表述。

| 前序容易误解的表述 | 本 Spec 的准确要求 |
|---|---|
| “任何输入都生成 Work” | 独立目标需要工作边界，但寒暄、解释、追问和局部修改不自动创建新任务、新项目或新成果。 |
| “彻底拆掉所有依赖” | 解除全局固定生产顺序；保留计算、转换、版本引用、明确业务规则和授权动作真正需要的依赖。 |

| “Artifact 降级” | 将成果类型与流程阶段解耦，不降低策略和成果的业务价值；FABE、MH 仍可以有专用结构与编辑器。 |

## 2. 目标、非目标与最小架构

### 2.1 本轮目标

同一套桌面工作台，不需要用户先进入固定专业模块，就能完成第 10 章的三类工作，并满足：

- 以工作目标决定采取哪些动作，而非以菜单或成果类型决定必走哪些阶段。
- 用户不懂技能名、CLI 参数和 harness 差异也能完成主要操作。
- 每项工作有独立输入边界、执行记录与成果关系；可追问、修改、切换和恢复。
- 用户能复用上一步的成果或分析结论，但系统不会自动替用户批准决策或实施外部动作。

### 2.2 本轮明确不做

不新增其他 harness，不重写 Codex 的执行循环，不新建通用工作流引擎，不建设完整 Marketing 本体/知识图谱，不做大规模营销 Skill 搜集和排名，不做自动安装任意社区代码，不做 Skill 自我改写与进化评估，不做完整 CRM/DAM/广告投放/社媒发布平台，不扩展企业级多人权限与审批中心，不以此次迭代为由全面更换视觉系统、框架或数据库。

真实渠道执行暂不作为通用性证明的前置条件。没有发布、CRM 或广告连接器时，能够给出有依据的执行方案及交接成果即可，但必须如实标明“未执行”。

### 2.3 四层结构及本轮落点

| 层级 | 职责 | 本轮工作 |
|---|---|---|
| 营销工作界面 | 对话、工作面、输入资料、成果查看与修改；对普通营销人员隐藏底层配置复杂度。 | 复用 v5 壳，补齐无项目工作、通用结果工作面与依据面板。 |
| 营销工作语义层 | 理解当前目标、工作范围、资料、成果关系和完成标准；不规定统一流程。 | 以轻量 Work 语义、Context 记录和成果引用实现，不强制独立服务。 |
| 能力与适配层 | 组织现有 skills/tools，说明适用任务、输入、输出、可用性；未来承接 Meta Skill。 | 做本地实际能力清单、可用性提示与最小反馈记录。 |
| 执行底座 | 会话、模型、工具调用、运行事件、权限请求和持久化执行状态。 | 复用本地 Codex 接入，修复上层适配；具体边界需要 Codex 核验。 |

“工作循环、专业领域、业务上下文”作为内部描述维度，不设计成用户每次都必须填写的三层分类表。Brand、Content、Social、Consumer、Performance 可作为搜索、能力发现和结果标签，不在本轮强制变成互斥一级模块。

## 3. 阶段 0：本地只读核查

### 3.1 必须回答的问题

| 核查项 | 需要取得的证据 |
|---|---|
| 项目身份 | 当前打开的工程目录、启动入口、包管理方式、有无 Git；不得假定远端仓库存在。 |
| v5 与本地映射 | 哪些页面/组件来自附件；哪些已经修改；附件锚点在本地的对应文件与调用链。 |
| 真实 Runtime 链路 | 用户输入从哪个处理函数进入服务端/桌面桥接，再进入 Codex；使用的版本、会话标识和事件映射。 |
| 模式分流 | 协作、计划、自主模式的入口、提示和权限设置；是否所有输入都被路由到固定内容计划。 |
| 固定约束 | 项目前置、产品资料前置、成果类型依赖、自动样例回退、类型级唯一成果、按项目聚合的运行状态。 |
| 现有对象 | conversation/thread/session、task、plan、artifact、run、source/ref、approval 分别如何存储和关联。 |
| 能力与文件 | 已安装或已接入哪些 skills/tools；哪些只是 UI 清单；本地文件授权、读取、输出目录和连接器如何实现。 |
| 版本与恢复 | 候选采用、历史版本、提交快照、取消/重试/重连是否真实支持；不能仅据按钮存在推断。 |
| 测试与数据 | 当前可运行的检查命令、已有定向测试、既有失败项、迁移或备份方式。 |

核查报告每项记录：**现状、文件/符号、证据、与 Spec 的差异、最小修改建议、验证方法**。不能从附件推断用户本地仍有相同缺陷。

### 3.2 执行边界

不得清理、覆盖用户未提交工作；不得未经要求初始化 Git、创建远端、push 或部署。先识别当前环境，再使用已有目录和命名约定。仅为实施此 Spec 必须新增文件时，说明新增原因。

若真实 Runtime 未接通或必要凭据不可用，可以继续完成可独立验证的修改和测试，但“真实集成验收”必须记为未验证/阻断，不能用模拟成功替代。

## 4. 工作与成果的最小语义契约

这些是产品行为约束，不是要求新建同名数据库表。若现有 conversation/session 已能承载，应优先增加最小元数据和关联，禁止同时造一套互相竞争的 Work、Task 和 Session 生命周期。

### 4.1 Work：一件持续协作的工作

一个 Work 表示一个当前目标及其持续协作过程。最小需要承载：稳定标识、标题/目标摘要、所属工作空间、可空项目关联、对话关联、上下文版本、成果引用和现有运行记录关联。

目标和成功标准允许由 Agent 从用户输入提炼，不要求先填表。简单查询只需要回答，不强制额外生成文件。

**默认关系：** 一个新会话承载一个主要工作目标，允许在会话里讨论、缩小范围、产出多个成果和修改版本。用户明确开启另一件无关工作时，提供“另开一项工作”；不能仅因检测到另一个营销词汇就拆分工作。暂不建设复杂多 Work/多会话编排。

| 输入情况 | 期望行为 |
|---|---|
| “帮我做一个品牌认知计划。” | 创建或初始化当前工作目标，可以没有项目。 |
| “为什么选择这个受众？” | 在当前工作内解释，默认不创建任务或成果版本。 |
| “把第三条写得更克制。” | 绑定已选成果和具体版本修改；对象不明确时作最少量澄清。 |
| “只给我分析，不要做计划。” | 缩小范围，不启动被排除的动作。 |
| “另开一个工作，分析另一品牌的数据。” | 新建独立上下文边界；不得继承原品牌业务资料。 |
| “把这份结论引用到刚才的内容计划。” | 显式引用指定结论/版本；保留来源，不搬走或覆盖原成果。 |

### 4.2 Project 与工作空间

Project 是可选的业务组织方式，不是执行资格。没有项目，不代表没有工作空间或文件权限边界：复用应用已有个人工作区/授权目录；若确实没有可写位置，只针对写文件这一动作请求选择目录，不强制创建营销项目。

关联项目默认是组织和上下文候选范围变化，不能自动重写当前成果。若关联会扩大候选资料范围，显示新增资料并按上下文规则决定是否提交。不得自动将工作附着到第一个项目或演示项目。

### 4.3 Artifact 与业务对象

Artifact 是可保存、可查看、可引用、可修改的工作成果。策略、分析结论、内容计划都可以成为成果；它们不等于某种文件格式。

- FABE、Message House 是可选专业成果结构，不是必须通过的阶段。
- POP、官网、电商等既有类型保留兼容。渠道、表达形式和成果类型在语义上区分，但本轮不为了命名整齐而强迁移所有旧枚举。
- 原始素材、素材集合和生成的内容成果应保留来源关系，不能仅因都涉及图片就合并为同一种对象。
- 同一工作可以包含多份同类型成果，例如五条社媒文案；查找和修改依靠成果 ID、版本及用户选择，不能只取 `kind` 对应的最后一份。
- 引用使用具体成果 ID＋版本或可靠的内容快照。上游有新版本时提示更新，不静默替换历史依据。

本轮不要求额外建立 Brand、Audience、Campaign、Insight、Decision 等完整关系数据库。相关信息可先作为现有资料、成果结构和标签承载。

### 4.4 Run、完成与正式动作

Run 是一次实际执行，不等于整项营销工作。模型回复结束可以显示“本次处理完成/成果已就绪”，不自动声称业务目标已经达成。

若已有任务状态机可用，沿用并说明映射，不新增平行状态机。结果生成、用户采用、正式批准和外部发布必须可区分：**生成不是采用，自检不是批准，导出不等于发布。** 通用分析和普通草稿不额外强加企业审批；已有正式要求仍按适用范围保留。

## 5. 修改包 A：入口与交互

### A-01：统一自然语言入口

首页和当前会话均支持直接说明工作目标、添加资料、引用已有成果。首页文案从单一“产品上市”扩大为“今天需要完成什么营销工作？”，但不强制更换品牌或重做视觉。

首页三个示例分别指向品牌策略、社媒内容和效果分析。示例点击用于填入示例请求/导入演示资料，不直接创建隐藏任务链，也不把演示资料带入之后的新工作。

项目选择保持可选、低干扰。创建项目和直接工作并存，不额外增加“必须先选营销类型”的步骤。

### A-02：沿用对话＋工作面的结构

保留 v5 的导航、对话区、Canvas/详情工作面、标签页、可调整布局和草稿保留。工作面用于可编辑成果，右侧检查面板用于工作依据和执行状态，避免同一信息同时散落三处。

最小区域分工：

| 区域 | 默认内容 | 不应承载 |
|---|---|---|
| 导航 | 新工作、最近工作、项目、现有成果/能力入口 | 以强制流程阶段作为唯一导航。 |
| 对话 | 目标讨论、补充输入、计划摘要、执行进展、结果解释 | 只允许选择预设指令。 |
| 工作面 | 当前成果、可操作表格/文档、版本比较 | 全部结果都渲染成相同的上市物料卡。 |
| 右侧面板 | 本次依据、缺口、执行状态；项目背景作为其中一个来源入口 | 冒充模型内部思维链，或只有静态项目属性。 |

优先复用现有标签和抽屉，不必须新增一级页面。常用桌面宽度下输入框、成果关键操作和取消入口不得被面板遮挡；本轮不新增移动端产品范围。

### A-03：两种熟练度，一套产品

一般用户看到业务语言：“需要哪些资料”“这份结果依据什么”“改哪里”“继续哪项工作”。技能名、工具参数、调用明细收在可展开详情中。

熟练用户可直接指定使用资料、排除方法、输出格式和执行范围。不要为这两类用户另造两套产品模式或强制新手向导。

### A-04：保留建议，去掉强迫

“下一步建议”可以有，但必须由当前目标与缺口产生。每次显示少量有意义的动作，如“比较两个定位方向”“补充缺失数据”“把结论转成下周内容计划”。建议不自动执行，用户忽略后不阻止继续提问。

用户声明“不需要后续内容”后，不再推送 FABE、MH 或物料制作。若当前任务已充分完成，允许结束，没有“必须往下走”的下一步。

## 6. 修改包 B：计划与依赖去固定化

### B-01：计划是当前目标的方案，不是统一清单

保留“协作 / 先定计划 / 自主完成”三种交互方式，但它们控制的是协作节奏，而不是三套营销流程。

| 模式 | 行为 |
|---|---|
| 协作 | 简单请求直接响应；需要多步时给出可调整的小计划，再按用户需求继续。 |
| 先定计划 | 输出目标、必要输入、拟采取动作、预期成果；用户确认前不启动制作或外部动作。 |
| 自主完成 | 在用户明确授权的目标和范围内连续执行；必要时暂停等待缺失输入或权限，不替用户正式批准/发布。 |

三种模式下，“解释这句话”“不要修改”“先停一下”都应按真实意图处理，不能一律转换成新制作计划。自主完成不是关闭运行时权限检查，也不等于默认开启最高权限。

### B-02：区分四种规则

| 规则种类 | 例子 | 处理 |
|---|---|---|
| 方法建议 | 做定位前可比较受众；写文案可参考 Message House。 | 可跳过，可由已有资料替代。 |
| 动作必要输入 | 分析转化率需要分子、分母及口径；修改需要目标版本；图像转换需要输入文件。 | 只暂停该动作；说明缺什么及可继续的部分。 |
| 明确适用的业务要求 | 用户选用的上市交付包要求某些成果；已核实且适用的品牌规则。 | 标明来源、范围和原因。不能把演示预设冒充全局组织制度。 |
| 权限/正式动作 | 对外发布、发送、覆盖正式文件、敏感写回。 | 复用真实权限与确认机制；不因“自由工作”而绕过。 |

**任何确实不能跳过的依赖，都应能解释为具体输入、业务约束或权限要求，而不能只解释为“上一阶段还没有做”。**

### B-03：已有上市链如何保留

将附件中的既有链路保留为一个可选择的上市能力组合/计划预设。用户要求“完整准备产品上市资料”时，可以建议使用；用户只要一条社媒文案时，不默认加入整套交付。

如果已有 Message House、批准文案、产品说明或可用素材，允许直接引用，不要求在当前项目重新生成 Strategy/FABE/MH。用户选择预设以后仍可调整范围；系统只对真正缺失的必要输入提醒。

### B-04：不另造规划底座

优先由现有 Agent loop 形成和调整行动方案，由上层呈现计划、记录引用和接收用户反馈。不要在前端写新的“营销任务关键词 → 固定阶段表”，也不要另建一个平行规划器去逐步控制 Codex 的内部执行。

若本地 Runtime 没有结构化计划事件，可以从应用层已确认的任务摘要形成展示记录；必须说明来源，不能把展示计划误报为 Runtime 已实际执行步骤。

## 7. 修改包 C：本次工作依据与 Context

### C-01：复用面板，增加三组内容

面板默认显示“本次工作依据”，可切换“执行状态”。项目属性保留，但不与本次实际输入混为一谈。

1. **本次提交/已读取：** 用户本轮资料、选中成果版本、适用品牌信息、已提交的相关历史摘要，以及执行期间工具实际读取的资料。
2. **待补充：** 影响当前动作的缺口；说明哪些工作仍能继续。
3. **未选用：** 在本次授权候选范围内被排除的资料及原因，如型号不匹配、时间不符、用户排除或与当前任务无关。

不扫描所有用户资料来凑“未选用”列表；不声称已经检查未读取的文件。

### C-02：“提交给 Agent”不等于“模型实际采用”

上下文可见性分级记录：

| 状态 | 允许的表述 |
|---|---|
| 候选来源 | “可供本次工作参考”，不能写成已读取。 |
| 已提交到本轮请求 | “已作为本轮上下文提交”，不能证明模型在推理中实际使用。 |
| 工具确认读取 | “本次执行已读取”，附工具记录/文件定位。 |
| 成果显式引用 | “此结论引用该资料/版本”，附成果位置与引用关系。 |
| 已排除 | “未提交到后续请求”，必须真实执行排除策略。 |

不得让模型自行生成一段漂亮的“用了哪些资料”描述，替代应用层请求清单和工具事件证据。

### C-03：最小上下文记录

复用已有存储，给每次 Run 保存最小 Context Snapshot，至少包含：所属 Work、请求目标与范围版本、用户选中资料/成果、排除项、提交摘要、来源版本或内容哈希、形成时间。敏感正文按既有权限保存，不为追溯新增无限量日志。

上下文组装的默认原则：先满足文件/账户授权和适用性，再取用户本次明确输入与指定来源，随后选当前工作必要历史和明确关联项目资料，最后才考虑相关偏好。用户偏好不能把错误事实变成可用证据；用户指定两个冲突来源时应显示冲突而非静默二选一。

当前工作的历史决策可以作为依据，必须标明是用户已确认还是 Agent 建议；不能将未经采用的建议自动升级为品牌事实。

### C-04：用户控制与历史会话

用户可以添加资料、排除一项、改选成果版本、编辑关键背景，并看到调整是否对下一次执行生效。运行中的请求固定使用启动时快照；修改后续范围不冒充已修改正在运行的输入。

**重要：** 从面板中排除资料，不等于能从已有 Runtime 会话记忆里抹去它。若底层已读过资料，而后续要求严格不再使用，应按本地支持能力重建干净执行会话或重编译必要历史；不具备该能力时如实提示限制，不展示虚假的“已彻底隔离”。具体实现需要 Codex 核验。

### C-05：缺口只影响必要部分

品牌规划不要求具体 SKU；只做文案不要求图片；没有销量数据可以分析已提供的互动数据，但不能声称完成销售归因。缺失信息用“可继续/需要补充”的实际工作提示表达，避免把所有任务卡在一个统一 `inputsReady` 字段上。

资料切换不得自动把另一品牌、市场或演示项目的默认事实补进来。无项目场景尤其要验证这一点。

## 8. 修改包 D：成果、能力与反馈

### D-01：通用结果兜底

已有专用编辑器继续复用。新增或复用以下通用承载方式：

| 结果形式 | 本轮要求 |
|---|---|
| 结构化文档/Markdown | 查看、编辑、版本、来源、导出。 |
| 表格/CSV | 列与数据预览、关键字段说明、保存或导出。简单内容计划支持编辑；分析原始数据只读，调整后形成派生版本。 |
| 图片、HTML 或已有可预览文件 | 使用现有安全预览能力，不以此为由新增图片/视频生成引擎。 |
| 暂无专用预览的文件/类型 | 提供可靠文件信息和打开/导出入口，不崩溃、不伪装已支持编辑。 |

未知 `kind` 不能导致核心流程失败。未知结果优先落在通用工作面，而不是要求用户选择最接近的“产品策略”类型。

模型生成的 HTML/脚本和社区能力描述均作为不可信输入处理。使用已有转义/隔离方案；不得为了动态工作面任意执行结果中的代码。

### D-02：同类型多成果与修改绑定

允许在同一个 Work 中创建多份同类型文案和多版不同方案。默认“新建一个方案”产生独立成果，“修改这个方案”在明确 ID/版本上产生候选版本。

局部修改必须携带目标引用，保留旧版。异步结果返回时若基础版本已变化，不静默覆盖：保存为待比较候选或提示冲突，使用本地最简单可验证的机制。

通用工作区默认只展示本 Work 的成果和显式引用。全局成果库仍可有“全部”视图，但该视图可见不等于所有内容都可自动进入本次上下文。

### D-03：能力清单，不是新插件平台

复用本地技能管理方式和 v5 能力入口。每个显示为可用的能力需要提供：名称、用途、适用工作、实现来源、版本/引用、需要的输入、可产生的结果、必要权限/依赖、当前可用性。

可用性至少区分：**已可用、需要配置/授权、仅演示、暂不支持**。只有已验证的本地能力才能默认显示“已可用”；社区知名度和安装数量不作为本轮未经调研的事实。

为三类验收任务使用本地已有的通用分析、文档写作和表格处理能力即可；不是必须安装三个名为“品牌/社媒/分析”的新 skills。没有特殊 Skill 时，可以由基础 Agent 完成其实际有能力完成的工作。

本轮不新增跨 harness 技能包规范。元数据与调用方式适配当前底座，避免把所有社区项目复制成自有代码。第三方能力仅在用途、来源和使用许可可核对的情况下纳入分发；不把未知许可证材料或嵌入字体二进制重新打包进本轮交付。

### D-04：Meta Skill 的最小接点

长期目标保留为“发现 → 推荐/组合 → 经授权安装 → 使用 → 根据反馈迭代”，但本轮不实现完整闭环。

仅记录足够的工作反馈：当次目标、使用的能力及版本、所引用资料、用户对结果的采用/修改/放弃、可选原因，以及工作完成情况。能复用现有活动和版本日志时直接复用，不另起事件平台。

不得将“用户没有点击”推断为能力不好；不得以一次修改自动改写共享 Skill；不得未经用户表达就把业务内容存为跨项目通用偏好。现有显式偏好保存能力可以保留。偏好、业务事实、来源文件与历史决策保持可区分，不都塞进一个“Memory”字段。

## 9. 修改包 E：真实 Runtime 与持久化

### E-01：实际请求链路

用户自然语言输入应经应用现有服务端/桌面桥接进入 Codex，不在前端模拟“已调用工具”。沿用已有认证和权限，不把密钥放入可导出的前端状态。

本 Spec 不指定某个版本的 app-server 方法名。实际协议、事件名、能力限制需要 Codex 依据本地依赖和实现核验，形成映射说明。

### E-02：执行记录绑定

每次运行在发起时绑定 Work/会话、项目关联、上下文快照、目标成果基础版本。后续事件按稳定标识回写，不依赖 UI 当前选择的 `projectId` 或打开的 Canvas。

切到工作 B 后，工作 A 的流式结果只能回到 A。重复事件、迟到事件和重连不能重复创建成果，也不能让已取消运行重新变成成功。复用既有事件处理，不要求为本轮新增并发调度平台。

若当前只支持单任务运行，保留该限制并正确显示“当前正在执行/可排队/需等待”，不要为了三类任务强加并行需求。

### E-03：取消、恢复和权限

以真实 Runtime 可提供的语义展示按钮。不支持真正暂停正在运行的模型时，不能通过停止 UI 动画伪装暂停；可以提供实际取消，或在下一个工具/步骤边界停止，但文案必须准确。

恢复前对照本地已存 Run 和底层会话状态；无法恢复执行位置时明确“重新执行未完成部分”或“重新发起”，保留此前成果，不虚构断点续跑。

工具权限和外部正式动作继续走已接入的确认流程；高层“自主完成”不扩张文件访问、执行权限或外部账户授权。

### E-04：模拟和真实完全可辨

离线示例可以保留，并标“演示数据/模拟执行”；真实模式只显示实际发生的读取、调用、结果和状态。不展示不存在的 PIM、MCP、内容库回执或实时研究来源。

工具不可用时给出可继续的范围和具体缺项。模型流式文本不是工具执行证明，画布已渲染也不是文件已保存证明。

### E-05：最小迁移

保留已有项目、会话、成果 ID、历史版本、引用和正式提交记录。能直接给已有会话补 Work 元数据就不做破坏性迁移。

历史成果归属明确时建立关联；归属不明确时保留为历史成果/项目共享成果，不按类型猜测归给最新会话。不批量把所有无项目成果归入同一个新 Work。

迁移前使用现有备份机制；迁移可重复执行而不重复生成对象。新旧状态若共存，记录唯一权威来源，避免双写分叉。具体迁移脚本、存储格式和回滚方法需要 Codex 核验后确定。

## 10. 三条验收故事与一个原型回归

以下场景是**设计的验收样例**，不是已发生的运行结果。每条都要经过真实自由输入链路；可以使用合成输入资料，但不能用按场景名称返回固定答案来通过真实 Agent 验收。

### S1：品牌战略——不依赖产品与物料

**用户角色：** 品牌营销人员。  
**入口：** 新个人工作，无关联项目。  
**输入：**

> 我在规划“北岚生活”这个虚构家居服务品牌的首轮品牌认知。接下来 90 天，先比较年轻租住人群和有孩子家庭两个受众方向。团队只能稳定维护两个内容触点，已有资料是两份内部访谈摘要。请提出有取舍的品牌沟通方向、触点建议和验证计划。不要制作产品文案，也不要创建上市项目。

**准备：** 测试目录提供两份明确标注“合成验收资料”的访谈摘要，内容足以支持两种不同的受众需求；没有真实市场规模或份额数据。资料的具体路径由 Codex 按现有工程组织创建，并在测试报告中记录。

**期待结果：** 一份品牌策略备忘录，说明基于输入的受众差异、推荐方向、取舍、两个触点的选择理由及如何验证。可以明确资料不足与工作假设，但不能凭空补市场占比。

**关键交互：** 用户追问“为什么没有同时覆盖两个人群？”时，仅解释；用户要求“保留当前方向，再补一个对照方案”时形成第二份候选，而不是覆盖第一份。

**验收重点：** 不要求产品型号，不生成 FABE/MH，不强制项目；依据面板只呈现本次品牌资料。输出体现业务判断，而非仅展示“调用成功”。

### S2：社媒内容——已有输入直接到成果

**用户角色：** 内容/社媒营销人员。  
**入口：** 新工作，可选择性关联现有内容项目。  
**输入：**

> 基于我提供的产品事实和已确认表达，准备下周 5 条社媒文案，受众是希望更好安排厨房日常的人。每条标明目标、切入角度、正文和建议行动。只要文字与排期表，不需要图片，不要重做 Strategy、FABE 或 Message House。

**准备：** 使用明确标注来源的演示产品事实、表达约束和一份可引用的既有文案；不要求新增生图或发布连接器。

**期待结果：** 一份可编辑内容排期表与五条可识别的文案条目。可采用“一个结构化成果含五条内容”或“一个计划＋五份关联成果”的已有最小实现；必须能稳定定位第三条，不以最新 `kind` 猜测目标。

**关键交互：** 选择第三条说“保留意思，改成更短、更克制，不改其余四条”；检查新候选只影响第三条或该成果中的第三项，原版本仍可查看。用户说“不需要下一步发布”后停止扩展动作。

**验收重点：** 不强制生成上游成果，不索要图片，不启动发布；用户提供的事实和旧文案可以直接成为输入；能处理同类型多个条目和局部修订。

### S3：运营分析——分析结果带动下一项工作

**用户角色：** 营销运营/增长人员。  
**入口：** 新个人工作，无关联项目。  
**输入：**

> 分析这两期社媒汇总数据。整体互动表现是否下降？区分内容结构变化与内容自身表现，给出两项最值得验证的调整。不需要写推广文案；先不要改排期。

**合成验收数据：** 数值是本 Spec 为测试而设计，不是美的或任何真实品牌业绩。

```csv
period,content_type,impressions,interactions
previous,practical_tips,30000,1800
previous,product_intro,10000,300
current,practical_tips,10000,650
current,product_intro,30000,900
```

**本测试专用口径：** 互动率＝互动次数÷曝光次数。这是此样例的约定，不暗示所有平台使用同一指标定义。

**可核对基准：**

| 指标 | 前期 | 本期 |
|---|---:|---:|
| 总曝光 | 40,000 | 40,000 |
| 总互动 | 2,100 | 1,550 |
| 总体互动率 | 5.25% | 3.875% |
| 实用知识内容互动率 | 6.0% | 6.5% |
| 产品介绍内容互动率 | 3.0% | 3.0% |
| 实用知识内容曝光占比 | 75% | 25% |

总体互动率下降 1.375 个百分点，但实用知识内容互动率上升、产品介绍内容持平。不能仅凭总指标下降就认定两类内容都变差。

可选算术分解：先用前期分组互动率乘以本期曝光权重，得到 3.75%；结构变化对应 -1.50 个百分点，分组互动率变化对应 +0.125 个百分点，合计 -1.375 个百分点。这是按指定顺序进行的描述性分解，不是因果归因或排期调整的效果证明。

**期待结果：** 可核对汇总表、指标定义、主要发现、两项建议实验及无法从这些汇总数据判断的事项。不得取两类互动率简单平均当作总体互动率；不得推断销量或广告收益。

**闭环交互：** 用户随后明确选择：“采用增加实用知识内容这个方向，另开一项工作，做下周三条内容的计划。”系统新建工作并引用原分析成果的指定版本；新工作带入用户选择的结论和必要数据摘要，不复制全部无关历史，也不自动声称该调整已经奏效。

**验收重点：** 数据可追溯、计算可复核、分析先于行动；没有发布能力也能完成“分析 → 用户选择 → 下一项工作”的产品闭环。

### R1：原有上市场景回归

用户明确选择完整上市方案时，原有 Strategy、FABE、Message House、素材、官网/POP 等能力仍可使用。已有成果可查看、编辑、引用、比较和导出；原有采用、检查、固定提交和批准记录不得损坏。

本轮不要求普通品牌工作走这条链，也不为了取消固定链而废掉用户已经能演示的专业工作面。

### 11.1 通用性额外检查

三条故事不等于“覆盖全部 Marketing”。它们只用来检查架构有没有被产品内容链锁死。

每条故事至少进行一次改写表达和一次输入变化测试，并补一个未预设任务，例如“将活动复盘纪要整理成待办与未决问题”。通过条件是复用同一入口、Context 和成果机制，而不是为第四个场景增加新的阶段序列。

输出不能只检查文件是否存在，还要由产品负责人或独立评审阅读：S1 是否真的有取舍，S2 是否符合输入与修改指令，S3 是否算对并区分事实与推断。模型自评记录不得标为人类专业验收。

### 11.2 分开报告三种证据

| 证据类型 | 能证明什么 | 不能替代什么 |
|---|---|---|
| 确定性单元/合同测试 | 状态、绑定、引用、取消、迁移和计算等行为正确。 | 不能证明真实模型任务质量。 |
| 真实 Runtime 运行记录 | 输入确实进入底座，实际工具/事件/成果正确回流。 | 单次成功不能证明普遍可靠。 |
| 人类任务验收 | 输出是否有营销价值、可读可用，交互是否顺手。 | 不能证明所有工程边界均被覆盖。 |

### 13.1 完成判定

同时满足以下条件，才可以声明“本轮修改完成”：

- 三类任务走同一真实 Agent 请求链路，且不被无关产品上市步骤卡住。
- 工作依据可调整并与真实输入记录对应；跨工作/成果/版本绑定可靠。
- 原有专业成果与正式提交边界得到保留；通用新任务有兜底工作面。
- 验收矩阵完成并附证据；未验证事项没有写成已通过。

如果尚缺真实 Runtime 或必要凭据，则明确交付为“代码/确定性验证完成，真实运行待核验”，不能标记全量完成。

## 14. 范围冲突时的裁决原则

**优先保留已经有效的能力，优先修正限制通用性的真实约束，优先复用现有结构。**

遇到以下情况按此处理：

| 情况 | 裁决 |
|---|---|
| 本地已经支持 Work 或等价语义 | 直接复用，不为满足文档名词再次建表。 |
| 本地已没有附件中的某个限制 | 标记已满足，补回归测试，不重新实现。 |
| 本地只有演示层而没有真实接入 | 如实记录，与用户口述的预期存在差异；不擅自宣称接入成立。 |
| 某依赖是明确适用的业务要求 | 保留并给出来源与范围，不作为所有工作统一门禁。 |
| 新工作缺一个专用编辑器 | 使用通用工作面，不因此再建一条 workflow。 |
| 某社区能力不适配当前底座 | 先用已有等价能力或说明缺口，不扩本轮为多 harness 平台。 |
| Runtime 不支持暂停/指定恢复方式 | 按真实能力提供取消/重试，不模拟能力。 |
| 改动会波及独立项目或真实外部系统 | 不越界执行；隔离受影响部分并说明。 |
